VideoMemory: Toward Consistent Video Generation via Memory Integration ​

项内容
arXiv2601.03655
提交日期2026-01-07
作者Jinsong Zhou, Yihua Du, Xinli Xu, Luozhou Wang, Zijie Zhuang, Yehang Zhang, Shuaibo Li, Xiaojun Hu, Bolan Su, Ying-cong Chen（HKUST(GZ)、HKUST、ByteDance）
分类cs.CV
一句话用 Storyboard / Memory / Visualization 三个 agent 维护一个按角色、道具、背景分库的动态记忆库，条目以文本索引加参考图存放、靠 LLM 语义匹配检索，缺失时先补生成参考图再入库，使多镜头视频里的实体外观有据可依。

所属教程：智能体视频生成

本页依据 arxiv.org/html/2601.03655v1 全文撰写。

§ 1 — 研究问题与重要性 ​

多镜头视频里跑偏的东西不止是主角的脸。第 3 个镜头里的咖啡杯到第 9 个镜头换了形状，客厅的沙发换了颜色，这些在观感上同样致命，而已有工作的注意力几乎全在人物身份上。VideoMemory 把"实体一致性"拆成角色、道具、背景三类分别处理，这个拆分本身就是它的第一个立场。

第二个立场关乎信息在哪里被保存。逐镜头生成的系统里，一致性信息要么活在模型的隐状态里（不可检查、不可编辑），要么活在上一帧的像素里（会累积漂移）。这篇论文把它显式地放进一个外部记忆库：每个实体一条记录，包含一个文本索引和一张参考图。这样"这个角色长什么样"就成了可以被读出、被审计、被人工替换的对象。

这件事的重要性在于它改变了故障的性质。隐式一致性坏掉时你只能重新采样碰运气，显式记忆坏掉时你能定位到是检索错了还是参考图本身就不对。

§ 2 — 前人工作与不足 ​

单模型直生（Wan2.2 直接按多条 prompt 生成）：表 1 里 K=4 时角色 0.34、道具 0.48、背景 0.25，是全表最弱的一档，且随镜头数增加无法维持。它没有任何跨镜头机制。

多镜头专用模型（EchoShot）：K=4 时角色 0.45、道具 0.59、背景 0.54，K=8 时降到 0.44 / 0.51 / 0.37。它在短故事上明显优于直生，但镜头数增加时三类实体同步退化，尤其背景掉得最快（0.54 → 0.37）。

上下文 LoRA（IC-LoRA + Wan2.2）：角色 K=4/8/12 为 0.42/0.55/0.43、均值 0.47；道具均值 0.43；背景均值 0.31。它能把参考信息塞进上下文，但容量有限，实体一多就互相挤占。

注意力共享（StoryDiffusion + Wan2.2）：角色均值 0.54，是对照里角色一项最强的之一；道具 0.47；背景 0.42。共享是全局的，无法区分"该共享角色外观"和"该共享房间陈设"。

分镜式 agent 流水线（VGoT + Wan2.2）：角色均值 0.57 最高，但道具均值只有 0.31，K=8 时道具跌到 0.22。这个反差很说明问题：它的一致性机制是围绕人物设计的，道具压根没有被纳入。

四类方法的共同缺口是没有一个可寻址的实体表。一致性被当成一种整体性质来优化，而不是逐实体地被记录和取用，所以"角色保住了、道具丢了"这种局部失败无法被系统本身发现。

§ 3 — 重建作者的思考路径 ​

先承认一个已有的能力事实：图像模型在给定参考图时保持外观的能力，明显强于视频模型在长时序上自我维持的能力。如果每个镜头的关键帧都能拿到正确的参考图，一致性问题就退化成一个检索问题。

接着问：参考图从哪来。故事的第一次出现处必然没有参考图，只能生成；生成之后应当被记下来，供后续所有出现使用。这就要求一个可写入的库，而不是只读的条件。

再问：怎么判断"这次出现的实体"和"库里那条"是同一个。字符串匹配立刻失效，因为脚本里同一个人会被写成"Anna""这个女孩""穿风衣的人"。可用的工具是 LLM 的语义匹配能力，把它当作检索器而非生成器。

最后问：匹配不上怎么办。硬造一张新图会引入新的外观；比较稳的做法是用已有的历史图像作为条件去生成新的参考图，让新条目继承旧条目的视觉血统，再写回库里。三个问题的答案连起来就是 Dynamic Memory Bank 的全部设计。

§ 4 — 核心 Intuition ​

把跨镜头一致性从"让模型自己记住"改成"把实体写进一张可寻址的表，用时取出来当参考图"。检索必须用语义匹配而非字符串匹配，因为脚本对同一实体的称呼一直在变；取不到时用历史图像条件生成新条目再写回，保证库随故事增长而不是一开始就要定死。

§ 5 — 具体方法与完整 Pipeline ​

三个 agent：Storyboard agent 把故事拆成镜头级脚本并标出每个镜头涉及的实体；Memory agent 负责记忆库的检索、写入与更新；Visualization agent 负责生成关键帧并补动画。

Dynamic Memory Bank：分角色、道具、背景三个子库。条目形如 m=(e,a,Iref​)，其中 e 是实体的文本索引（论文中的例子形如 Anna_1985）、a 是属性描述、Iref​ 是以 PNG 存放的参考图。检索由 LLM 做语义匹配，不做字符串匹配；匹配失败时用历史图像作为条件生成新的参考图并写回库中。

实现后端：LLM 用 Gemini 2.5 Pro，关键帧用 Gemini 2.5 Flash-Image 生成，动画化用 Wan 2.2 I2V-14B。

一个具体例子：故事第 2 个镜头首次出现"Anna 拿着一只蓝色马克杯站在客厅"。Memory agent 在三个子库里都查不到对应条目，于是 Visualization agent 生成关键帧，并把 Anna、蓝色马克杯、客厅分别注册成三条记录。到第 9 个镜头脚本写"她把杯子放到桌上"时，LLM 把"她"匹配到 Anna_1985、把"杯子"匹配到蓝色马克杯条目、把当前场景匹配到客厅条目，取出三张参考图作为关键帧生成的条件，再交给 Wan 2.2 I2V 补出运动。

评测设置：自建 benchmark 共 54 例 = 3 个子类 × 3 种镜头数（K=4/8/12）× 6 个样本。指标只取每个镜头的中间帧计算 DINOv2 特征相似度：角色用 Mediapipe 裁出人脸，道具用 Grounded SAM 分割，背景用整帧。镜头数不足（欠生成）的情况会在归一化时被惩罚。

§ 6 — 核心数学推导 ​

本文没有定理或收敛性分析，形式化只有记忆条目的结构与评测指标的定义，这里把后者讲清楚，因为它决定了全文结论的可信范围。

对第 k 个镜头取中间帧 xkmid​，按实体类别裁出感兴趣区域 R(⋅)，与该实体的参考图 Iref​ 一起过 DINOv2 编码器 ϕ，取余弦相似度：

sk​=∥ϕ(R(xkmid​))∥⋅∥ϕ(R(Iref​))∥⟨ϕ(R(xkmid​)),ϕ(R(Iref​))⟩​,

再对 K 个镜头取均值并按实际生成的镜头数做归一化惩罚。

这个定义有两条必须写明的性质。第一，它只看一帧，镜头内部的时序退化（人物中途变形、道具消失后又出现）完全不进入统计。第二，它是相似度而非"变化合理性"，一个把参考图原样贴进画面的退化解会得到接近 1 的分数。第二条在 §11 会被展开成攻击方案。上式中的 ϕ、R 是我按论文描述的流程（Mediapipe 裁脸、Grounded SAM 分割、整帧背景、DINOv2 相似度、欠生成惩罚）写出的形式化，论文正文用文字描述了同一流程。

第一个问题：显式记忆能否同时管住三类实体。角色均值 0.63 对最强对照 0.57，道具 0.58 对 0.47，背景 0.72 对 0.45。三类同时领先，且优势在背景上最大。这符合方法的结构预期，因为背景是最容易被已有方法忽略的一类，而记忆库给了它一个独立子库。

第二个问题：镜头数增加时会不会退化。VideoMemory 的角色 0.61/0.65/0.64、背景 0.71/0.72/0.73 在 K 从 4 到 12 基本持平，而所有对照都随 K 起伏甚至大幅下滑（VGoT 的道具 0.48 → 0.22）。外部记忆库不随镜头数衰减，这一点比绝对分数更有说服力，因为它是机制本身的直接推论。道具一列 0.69/0.50/0.55 有明显波动，说明道具的检索与保持仍不稳。

第三个问题：收益是否来自记忆库本身。消融（表 3，8 镜头均值）去掉 Dynamic Memory Bank 后角色 0.65 → 0.51、道具 0.50 → 0.43、背景 0.72 → 0.28。三个数字与表 1 的 K=8 列完全对得上，列序因此得到交叉验证。背景的落差最大（0.44 个绝对点），说明全文最亮的那一项几乎完全由记忆库贡献。

User study：5 名评分者、270 组强制二选一，最高偏好率 95.8%。5 人的评分者规模偏小，这个数字应当读作定性支持而非统计结论。

§ 8 — Take-aways ​

5 句版：把一致性做成一张可寻址的实体表，比让模型隐式记住更容易审计与修复。实体必须分类型管理，角色、道具、背景的失败模式不同，已有方法在道具上的崩塌（VGoT 0.48 → 0.22）就是混为一谈的后果。检索必须是语义匹配，脚本对同一实体的指称一直在变，字符串匹配从第一句就会失效。记忆库的最大结构优势是不随镜头数衰减，K 从 4 到 12 角色与背景几乎持平。消融显示背景一项 0.72 → 0.28，全文最强的结果几乎全由记忆库贡献。

3 句版：三个 agent 维护一个按角色/道具/背景分库的动态记忆库，条目是文本索引加参考图，用 LLM 语义检索、缺失时条件生成后写回。角色 0.63、道具 0.58、背景 0.72 三项全面领先，且对镜头数不敏感。评测只取中间帧算 DINOv2 相似度，对"复制粘贴"式退化解不设防。

1 句版：给多镜头视频配一个可读可写的实体记忆库，一致性就从隐式性质变成了检索问题。

§ 9 — 最脆弱的假设 ​

最脆弱的一条是：LLM 能把脚本里的每一次指称正确地映射回记忆库中的唯一条目。整个方法的正确性挂在这一步上。检索错了不是"效果差一点"，而是把错误的参考图注入生成，让 B 的脸长到 A 身上，且这个错误会随写回机制固化进库中，污染后续所有镜头。

这条假设在实践中很容易破。故事里出现两个外观相近的角色、同一件道具有多个实例（桌上三只一样的杯子）、场景是同一栋房子的不同房间时，语义索引本身就有歧义。论文的记录形式（文本索引加属性描述）没有为"实例编号"提供结构，Anna_1985 这样的索引里也看不出如何区分同名不同实例。

论文为它提供的证据是间接的：表 1 与表 3 显示引入记忆库后指标全面上升，说明在该 benchmark 的 54 例上检索总体是work的。缺的证据是检索本身的准确率——没有报告"检索命中率"这样的中间指标，也没有针对多实例歧义构造压力测试。54 例的规模也很难覆盖到这些边角。因此现有实验能证明"有记忆比没记忆好"，不能证明"检索足够可靠"。

§ 10 — 最小复现实验 ​

一周内可做，且只需验证最关键的那一环：

  1. 不实现完整三 agent 流水线，只实现 Memory agent 的检索部分：构造一个含 20 条实体记录的库（10 个角色、5 件道具、5 个背景），其中刻意放入 3 组易混淆项（两个同性别同发色角色、三只同款杯子、同一栋房子的两个房间）。
  2. 写 200 条镜头级脚本句，人工标注每句应当命中的实体条目。
  3. 对比三种检索：字符串匹配、CLIP 图文相似度、LLM 语义匹配。
  4. 测检索命中率，并单独报告易混淆项子集上的命中率。
  5. 判据：若 LLM 语义匹配在整体上远高于字符串匹配，方法的核心设计得到支持；若它在易混淆子集上掉到接近随机，则 §9 的脆弱性被证实，说明记忆条目需要实例级 ID 而非仅有语义索引。

这个实验完全不涉及视频生成，成本极低，但它测的正是全文最没有被量化的一环。

§ 11 — 最强反例设计 ​

最强的攻击针对评测协议。指标只取每个镜头的中间帧、计算它与参考图的 DINOv2 相似度，而 pipeline 恰恰是直接复用同一张参考图去做关键帧条件。这构成一个结构性的循环：方法把参考图的外观搬进画面，指标又去测画面与参考图有多像。

据此构造平凡基线：跳过所有生成，直接把 Iref​ 本身当作每个镜头的中间帧输出（配上任意运动即可，因为运动不进入指标）。这个基线的 sk​ 按构造等于 1.0，将超过表 1 中所有方法，包括 VideoMemory 的 0.63/0.58/0.72，而它的叙事价值为零。指标无法惩罚它，因为它没有任何"变化合理性"的项。

这不是纯理论构造。ViStoryBench 一类评测已经为此设置了 Copy-Paste 指标，专门检测生成结果是否只是把参考图贴回画面，而本文没有报告这类指标。因此对表 1 的一个完全成立的替代解释是：VideoMemory 领先的部分原因是它比对照更倾向于直接复用参考图外观，而这在指标上被记为优点、在观感上可能是缺点。

可执行的检验有两步：其一，报告平凡基线的得分作为指标上界；其二，加入 Copy-Paste 类指标与镜头内多帧采样（而非只取中间帧），看排序是否改变。若排序稳定，本文的结论会更强；若排序翻转，则表 1 度量的主要是复用强度。

§ 12 — Follow-up Research Idea ​

驱动 idea 的局限是：记忆条目是一张静态参考图，它把"这个实体长什么样"和"这个实体此刻处于什么状态"混成了一件事。故事推进时实体会合法地改变——衣服湿了、杯子空了、房间被弄乱了。当前设计要么让这些变化被参考图拉回去（一致性指标上升，叙事崩坏），要么让它们改写参考图（后续镜头继承了新状态，但库里失去了原始身份）。两条路都不对，因为身份与状态被压在同一个槽位里。

可借鉴的相邻工具是数据库领域的时序表与实体-属性建模：把条目从 (e,a,Iref​) 升级为"不变的身份签名 + 带时间戳的状态序列"，检索时按身份取签名、按当前镜头时刻取状态，条件化时把两者分别注入（签名管外观，状态管可变属性）。这也顺带给 §11 的攻击提供了防御，因为状态序列的存在使得"原样复制"在时序上是可被检测的。

第一个实验：构造 60 条含单一不可逆状态变化的故事（打翻、点燃、弄湿、撕破），对比现有单槽位记忆与身份/状态双槽位记忆，测两个量——身份相似度（应保持）与状态正确率（应随剧情改变）。若单槽位方案在两者之间只能取一头，双槽位能同时保住，就证明这个拆分是必要的，而不是又一个模块。
