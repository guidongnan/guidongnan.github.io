The agent that would not look

August 2026 ~7 min agents · tools · evaluation

I built an agent with a planner, episodic memory, retrieval over a failure-mode library, a skills document it maintains about itself, and eight tools. On a matched set of tasks it lost to a fixed generate → verify → repair loop, while spending about three times the tokens. Everything I did to make it smarter made it worse. The thing that finally worked was embarrassingly dumb, and I think it generalises.

The setting: an agent writes a small program, a solver runs it, and a harness measures whether the program actually produced the event it claimed. I will keep the domain vague because parts are not mine to publish, but nothing below depends on it.

The agent lost

The fixed loop is what everyone builds first. Generate, verify, repair, N times, with the verifier at the centre and no decisions to make. The agent inverts that: it plans, then chooses one action per turn, observes the result, consults its memory and its own notes, and decides when it is finished. The verifier becomes one tool among eight.

On twelve matched tasks, the fixed loop solved seven. The agent solved six, having spent roughly three times as many tokens getting there. That is a bad result and I sat with it for a while, because on paper the agent strictly dominates: it can do everything the loop does, plus choose.

My first instinct was that it was wandering — spending its budget on exploration and running out of room to land the scene. So I added a nudge: when three steps remain, wrap up. That took it from six to three. Worse than the loop, worse than itself, worse than one-shot.

Then I changed one variable and nothing else: I raised the step budget from fourteen to twenty-four. It went to eight, past the fixed loop. Same agent, same tools, same prompt, same tasks.

So the agent's advantage was never autonomy in the sense I had been imagining — good judgement about what to do next. It was that autonomy let it spend more, better-targeted iterations. When I capped the iterations, all the machinery underneath was just overhead.

Zero times

The other half of the diagnosis is the part I find funniest and most useful.

In the original design, the harness — the thing that measures whether the program did what it claimed — was available as a tool. The agent could call it whenever it wanted. It had a retrieval tool over a library of previously diagnosed failures, too. Both sat there in the tool list, described clearly, alongside write_code and run_backend.

Across an entire run, the agent called the retrieval tool zero times. It rewrote code blind, over and over, guessing at what had gone wrong.

I want to be precise about why this is interesting, because "the model didn't use my tool" is a boring observation on its own. The interesting part is what it says about where information has to live. The agent was not incapable of using the harness; when I invoked it manually the agent used the result perfectly well. It simply never chose to look, because looking costs a turn and produces no visible progress, while writing more code feels like progress and is what the whole system was nudging it toward.

The fix was to stop offering and start pushing. Now, after every successful run of the program, the tool result is the full measurement block: what the program achieved, what constraints it violated, which known failure modes fired, and the relevant retrieved repair notes. The agent does not decide to look. Looking is what running returns.

I have started treating this as a design rule rather than a bug fix. If a piece of information is necessary for the agent to do the task correctly, it does not belong in the tool list. It belongs in the observation. Optional access to the truth is, in practice, no access to the truth.

It was the budget, and that is a boring answer

Put the two findings together and the story is unglamorous. The agent's memory, its retrieval, its self-written notes — none of that was the lever. The levers were:

  • How many repair rounds it gets. Dominant, by a distance.
  • Whether the measurement is unavoidable. Second, and it is what makes extra rounds worth anything, because a round without feedback is just another blind draft.

This lines up with something I saw on a larger benchmark in the same project: an arm that draws five independent programs and keeps whichever its own verifier likes best barely beats one-shot, and loses to plain repair. Five tries at guessing is not the same resource as one try plus a measurement, even when the five tries cost more.

There is a version of this I would like to be wrong about, so let me state the limit clearly: my agent comparison is twelve tasks. Twelve. The direction was stable across the variations I tried and the mechanism is legible, but I would not put a confidence interval on it, and I have not yet re-run the pushed-harness agent over the full bank.

Learning that only moves forward

One piece of the machinery I do still believe in, mostly because of how it fails.

The agent maintains a document of its own lessons. It starts completely empty — nothing seeded, no examples. After each episode the agent distils what it learned into a section and merges it in. The merge is constrained so that it can only add or refine, never delete. And if a malformed reply parses to zero lessons, the document is left exactly as it was.

That last clause is the one that matters. It means a bad generation cannot erase accumulated knowledge; the worst case is a wasted turn. Learning is monotone. I would rather have a slightly bloated document that only grows than a tidy one that can silently forget the thing that took me two days to diagnose.

The retrieval over it is deliberately plain — term frequencies, no embeddings. The match here is lexical, because symptoms and fixes share concrete nouns, and a plain index re-indexes in milliseconds when the agent's own document grows mid-run. A dense retriever would have bought me very little and cost me the ability to re-index on every write.

The memory of past episodes is ranked by mechanism first and scale second, on the theory that a topple is a topple whether it is a bookshelf or a domino. Successful episodes get a small preference bump — small enough that a failure with the same mechanism, which is more likely to be on point, still outranks a loosely related success.

What I take from it

Three things, in order of how much I would defend them.

Necessary information goes in the observation, not the tool list. I am fairly confident this generalises well beyond my setting. Anything the agent must consult to be correct, it will eventually not consult.

Count repair rounds before you count anything else. When an agent underperforms, the reflex is to improve its reasoning — better prompts, better planning, better memory. In my case the entire gap was iterations, and every reasoning improvement I made was invisible next to it. Sweep the budget first; it is cheap and it tells you whether you are even looking at the right variable.

Autonomy is a way of spending, not a source of quality. The agent is better than the fixed loop, but not because it chooses wisely. It is better because it can decide to keep going when the loop would have stopped. That is a real advantage and worth having. It is just not the one I was telling myself I had built.
