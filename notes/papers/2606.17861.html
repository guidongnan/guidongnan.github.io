GameCraft-Bench: Can Agents Build Playable Games End-to-End in a Real Game Engine? ​

项内容
arXiv2606.17861
提交日期2026-06-16
作者Tongxu Luo, Rongsheng Wang, Jiaxi Bi, Chenming Xu, Zhengyang Tang, Jianlong Chen, Juhao Liang, Ke Ji, Shuqi Guo, Yuhao Du, et al.
分类cs.CL
一句话让 coding agent 在真实 Godot 工程里从自然语言规格造出可启动的完整游戏，并连同自己录制的回放轨迹一起提交，验证器重放这些轨迹录成视频、再用隐藏 rubric 让多模态裁判打分，把评测从「代码是否正确」换成「交互系统是否正确」。

所属教程：世界模型

§ 1 — 研究问题与重要性 ​

游戏生成正在变成 coding agent 的一个新应用面：模型要把自然语言规格变成可玩的交互系统。但它和普通编码任务有一处结构性差别——游戏行为不是由源码单独定义的，而是由脚本、场景、资源、渲染、运行时交互在引擎里共同产生的。一个方法签名正确、单测全绿的项目，可能启动就黑屏、按键无响应、碰撞判定反了、UI 完全不可读。

论文因此主张：评测这件事必须回答三个递进的问题——agent 在哪里开发、交付什么产物、结果如何被判定。它把答案固化成三条 desiderata：Engine Grounding（必须在真实引擎里开发，面对场景层级、脚本生命周期、资源加载、输入分发、物理、渲染、工程配置、启动流程这些真实集成问题）、Artifact Completeness（必须交付可启动的完整工程，而不是散落的脚本或视觉上像游戏的片段）、Interactive Verification（必须通过实际的玩家输入与回放来判断，而非静态检查）。三条合起来把评测目标从 code correctness 移到 interactive system correctness。

§ 2 — 前人工作与不足 ​

现有游戏生成 benchmark 各自满足一部分契约，但没有一个三条全占。OpenGame-Bench 满足 Artifact Completeness——它要求 agent 从开放式 prompt 生成完整游戏——但目标是 Web 游戏而非真实引擎工程，判定也主要停在静态或页面级检查，不通过游戏交互。GameDevBench 满足 Engine Grounding——它把评测搬进了 Godot——但研究的是从教程衍生出来的局部编辑与确定性测试，考的不是完整游戏的构建与可玩性。与本文设定最接近的是并行工作 WebGameBench，它通过真实浏览器交互评测交付的 Web 游戏，但仍在引擎原生开发之外，而且依赖评测侧的自主探索去发现玩法。另有 GameGen-Verifier 用运行时状态注入改进验证，但不评测从规格出发的开放式构建。

更广的软件工程 benchmark（SWE-agent、OpenHands、ChatDev、MetaGPT 所面对的那一类）几乎都通过代码补丁、单元测试或 issue 解决来判定正确性，其隐含假设是「可执行行为能被静态产物充分刻画」。端到端游戏生成恰好证伪这条假设。GUI agent 侧的 Mind2Web、WebArena、OSWorld 强调交互式的任务完成，但目标是操作既有界面，不是合成可执行的软件产物。

「评测侧自主探索」为什么是个真问题？因为一旦验证器需要自己摸索每个游戏该怎么玩，分数就变成了验证器探索策略的函数——同一个游戏换个探索策略可能得完全不同的分，跨任务、跨提交都不可比。

§ 3 — 重建作者的思考路径 ​

从已知的失败模式倒推。已知一：静态检查会给「看起来像游戏」的东西发分，而这类失败（控制无响应、敌人不动、目标不可达、UI 缺反馈、状态转移断裂）只有在玩起来之后才暴露。所以必须运行。已知二：一旦要运行，就得决定「谁来玩」。人来玩不可扩展；写死的通用输入序列对不同游戏没有意义；让验证器自主探索则把评测本身变成了一个开放的探索问题，引入不可控的方差。

剩下的可能性不多：让 agent 自己提交怎么玩。这是一个有代价但清晰的取舍——交互过程被固定下来，评测仍然发生在真实玩家输入之下，而验证器不必猜。作者显然意识到这会引入新的失败模式，所以在打分侧加了两道防线：一是 build gate，工程起不来直接 0 分；二是隐藏 rubric，agent 看得到规格但看不到评分细则，避免规格退化成检查清单。

已知三：要大规模、可复现、无 GUI 地跑起来，引擎选型是硬约束。论文列了一张表：Godot 开源、安装轻、支持命令行/headless、原生 2D、场景与工程文件是文本格式；Unity/Unreal/GameMaker 在这几条上分别有重型安装、许可限制、编辑器中心工作流或二进制工程格式的问题。

已知四：rubric 需要既能被自动打分、又不能只考「跑得起来」。作者从游戏设计文献取维度——MDA 框架给出 Core Mechanics（规则与状态转移）、Content Depth（运行时规模与进程）、Art and Presentation（被创作的感官层），playability heuristics 给出 Functional Visuals（游玩中的可读性与视觉反馈）。

§ 4 — 核心 Intuition ​

游戏的定义性属性是「动作—反应」回路，而这个回路里的绝大多数失败在被玩之前是不可见的。要自动化地看到它，就必须有人来按键；既然不能让评测器自己去猜每个游戏怎么玩，那就让造游戏的人顺便交一份怎么玩的说明书——把开放式交互压成可重放的确定性证据，交互过程固定，被评的仍然是真实运行中的行为。

§ 5 — 具体方法与完整 Pipeline ​

以任务 Strategy-Skirmish（暗黑幻想风格的网格战棋）为例，五个阶段：

  • Stage 1 任务打包。 每个任务打包三样东西：面向产品的自然语言规格 instruction.md（玩家幻想、核心循环、机制、目标、内容规模、美术方向、期望演示场景，明确写「不是原型，是可上架的完整微型游戏」）；Godot 开发与运行环境（可编辑工作区、引擎与工具链、只读挂载的 Kenney CC0 与 OpenGameArt 素材库、截图助手、提交契约）；以及隐藏的 tests/rubric.json。rubric 把同一份意图拆成四类可观测要求（前缀 M / D / V / A），总条目不超过 24 条。
  • Stage 2 agent 生成。 agent 可以建场景、写脚本、配输入动作、用共享素材、运行工程、看截图、按工具反馈迭代。必须交两样：完整 Godot 工程 G，以及 1–10 个回放轨迹 Π（放在 demo_outputs/，JSON 记录 1280×720 视口下带帧号的鼠标键盘事件，可带 scenario 标识以确定性地直接进入某个状态，如战斗中、升级界面、终局）。轨迹不属于游戏本身，是评测证据。
  • Stage 3 build gate。 验证器解析工程与轨迹、在 benchmark 运行时启动工程、检查是否达到可运行状态。起不来或没有一条可解析轨迹，BUILD=0，总分直接为零。
  • Stage 4 重放。 每条有效轨迹起一个全新 Godot 实例，在固定 1280×720 视口下以 30 fps 重放事件，ffmpeg 录屏，按 0.5 秒采样（即 2 fps）抽帧。默认最多 10 个 demo、每个最多采样确定性的 20 秒窗口。
  • Stage 5 打分与聚合。 多模态裁判（GPT-5.5）按隐藏 rubric 对采样帧逐条打 0/0.5/1 分，输出严格 JSON。聚合规则按条目语义分化：场景特定的要求取 max（看到一次即证明存在），持续性属性（可读性、视觉反馈、美术一致性、UI 不重叠）取 mean。

runtime 细节：Harbor 框架、本地子进程沙箱、Ubuntu 22.04 + Python 3.12 + Godot 4.6.2，Xvfb 提供无头显示、xdotool 合成输入、ffmpeg 录制；agent 超时 7200 秒、验证器 1800 秒，不额外限制工具调用次数。

质量控制：12 名有丰富游戏经验的标注者，每个任务同时写规格与 rubric，然后写一个 oracle 解法（Godot 里的最小可玩草稿）做交叉验证——检查规格在引擎里可实现、请求的行为能通过重放展示、每条 rubric 对应可观测状态而非主观偏好。oracle 到不了目标状态或 rubric 条目在重放里找不到证据，就回去改规格与 rubric 再验一遍。

§ 6 — 核心数学推导 ​

任务形式化为 τ=(s,E,ρ)：规格、环境、隐藏 rubric，其中环境 E=(R,W,A,C) 分别是 Godot 运行时与工具链、可编辑工作区、共享资源接口、提交契约。agent 观测到 (s,E) 但看不到 ρ，必须产出

y=(G,Π),Π={πi​}i=1n​

验证器启动 G 并重放 Π 得到游玩观测 O=ReplayR​(G,Π)，成功的提交即观测行为 O 在 E 的约束下实现了 s。最终分数

Score=BUILD×(wM​M+wD​D+wV​V+wA​A)

默认权重 (wM​,wD​,wV​,wA​)=(0.15, 0.35, 0.15, 0.35)。这组权重不是中性的：它把三分之七的分量押在 Content Depth 与 Art and Presentation 上，作者的理由是「完整的游戏应该超出最小机制与功能原型」。BUILD∈{0,1} 是乘性门，意味着任何构建失败都不可用其他维度补偿——这是一个刻意的、非线性的设计选择。

§ 7 — 实验设计与结论 ​

当前前沿 agent 到什么水平？ 七种配置在全部 140 个任务上跑：Claude Code + Opus-4.7 high 拿到最高的 41.46%，Codex + GPT-5.5 high 39.49%，Kimi Code + Kimi-K2.6 30.65%，Claude Code + MiMo-V2.5-Pro 24.10%，Code Buddy + GLM-5.1 18.29%，Code Buddy + MiniMax-M2.7 10.95%，Codex + DeepSeek-V4-Pro 仅 2.15%。结论：端到端游戏生成远未解决，最强系统也只到四成。

低分是哪一类能力缺失？ 分维度看，强 agent 的 Core Mechanics 明显高于其余三项：Opus-4.7 55.34 / GPT-5.5 54.36 / Kimi 39.76，而 Content Depth 分别是 39.48 / 38.61 / 28.07，Art and Presentation 更低（Opus 36.86）。结论：agent 常能造出可辨识的局部机制，但拼不成有足够内容、可读反馈与统一呈现的完整系统。

跑得起来 ≠ 拿得到分。 图 6 把 launchability 与可重放证据分开统计：多数强 agent 满足基本执行契约，但最终分仍低。DeepSeek-V4-Pro 是极端案例——它常常忽略或违反轨迹提交要求，build pass 率与 valid trace 率之间出现巨大落差，2.15% 的分数主要由此产生。结论：闭合 build–replay–evaluation 全环路本身就是一项独立的能力。

看画面有没有用？ Kimi-K2.6 在 140 个任务里做了 2998 次渲染画面检查（平均 21.41 次，中位数 19，只有 4 个任务完全没截图），Opus-4.7 调用 1952 次（13.94），GPT-5.5 只有 268 次（1.91）。案例显示 Kimi 反复看帧、修正单位摆放错位与选中高亮缺失、调整网格与回合指示器布局。结论：渲染反馈能暴露源码里看不见的失败，把游戏生成从一次性代码合成变成感知引导的迭代。

多干活有没有用？ MiMo-V2.5-Pro 呈现典型的 write-first / bash-heavy 模式：先快速铺完整套文件，再进入以 shell 为主的调试期，bash 占全部工具调用的 56.3%，Read + Edit 只占 16.5%；每任务工具调用中位数 128，而分数与调用总量的相关系数只有 r=+0.016。五个零分任务全部构建成功但一条 demo 轨迹都没提交。结论：执行量是最终可玩性的弱预测因子；瓶颈是结构性的（有没有闭环）而非努力程度。

裁判可靠吗？ 固定同一份游玩证据、只重跑 GPT-5.5 裁判 10 次，Kimi-K2.6 在 Card Game / Simulation 上标准差 0.0037 / 0.0038，Opus-4.7 为 0.0050 / 0.0036，远小于 agent 与任务族之间的差距。人工校准（三个任务族，Kimi 提交）显示裁判总体偏宽松 +3.32 个百分点，且偏差有方向性：人类在 Content Depth 与 Art and Presentation 上更严，裁判在 Functional Visuals 上更严；Idle 族偏差最大（+8.76）。结论：重复评分稳定，但存在温和且分维度不均的宽松偏差。

四个维度是同一种能力吗？ Kimi-K2.6 上 M–D 相关 r=0.61、M–V r=0.53，而 A–V 只有 r=0.11。结论：能力部分可分解，机制强不自动带来呈现好。

§ 8 — Take-aways ​

5 句话版。 GameCraft-Bench 把端到端游戏生成形式化为「把规格变成可玩交互系统」，并提出三条评测契约：真实引擎、完整产物、交互验证。它的关键工程选择是让 agent 连同游戏一起提交可重放的输入轨迹，从而在保留真实玩家输入的同时，避免验证器自主探索带来的方差。140 个 Godot 任务覆盖 15 个游戏族，评分是 BUILD 门乘以四维加权和，权重刻意偏向内容深度与美术呈现。七个前沿配置里最高只有 41.46%，且分维度呈现「机制 > 内容 > 视觉 > 呈现」的一致梯度。分析给出三条可操作的发现：看渲染画面有助于调试、工具调用量与分数几乎无关、四个维度并非同涨同落。

3 句话版。 游戏的失败大多只在被玩的时候才暴露，所以评测必须运行、必须有人按键。让 agent 自己交回放轨迹，把开放交互压成确定性证据，代价是分数同时衡量了「造游戏」和「演游戏」两件事。当前最强 coding agent 能造出可辨识的机制，但造不出完整、可读、有呈现质量的游戏。

1 句话版。 可执行的创意软件必须被交互地验证，静态代码检查、构建成功与视觉合理性都不够。

§ 9 — 最脆弱的假设 ​

最要命的一条：agent 提交的回放轨迹是对其游戏的忠实、无偏的展示。 整套 Interactive Verification 的证据链都由被测系统自己生成——这在评测方法学上是一个罕见的让步。

它在实践中为什么可能不成立？两个方向。低估方向：一个游戏做得不错但不擅长写轨迹的 agent 会被系统性惩罚。DeepSeek-V4-Pro 的 2.15% 与 MiMo-V2.5-Pro 那五个「构建成功但零分」的任务就是活例——这些分数几乎不含任何关于游戏本身质量的信息。高估方向：rubric 里场景特定的条目采用 max 聚合，意味着某个特性只要在一个 demo 里被看到一次就能拿分。一个懂得取巧的 agent 可以专门录一条只走标题界面和一段脚本化演出的轨迹，用它去命中 Art and Presentation（权重 0.35）与部分 Content Depth 条目，而完全不暴露核心循环的破绽。评分公式里 Core Mechanics 只占 0.15，这个激励方向并不安全。

论文给了什么证据？它意识到了这个取舍并在标注指南里明确要求「max 只在观察一次足以证明其存在时使用，且要保守，避免过度奖励静态演示」，还要求弱证据（仅有标签、纯装饰、静态、与玩法脱节、只靠颜色区分、由默认控件或原始几何图形堆成）最高只能给 0.5。它还用 oracle 解法验证每条 rubric 都对应可观测状态。缺什么证据？没有任何实验把轨迹固定住——比如用人工或 oracle 编写的第三方轨迹去重跑所有提交，看排名是否稳定。没有这一步，「游戏质量」与「演示编写能力」在最终分数里始终是混淆的。

§ 10 — 最小复现实验 ​

不复现 140 个任务，只做解耦实验：

  • 样本。 从 15 个游戏族各取 1 个任务，收集两个 agent（比如 Opus-4.7 与 Kimi-K2.6）在这 15 个任务上的提交工程，共 30 份。
  • 实现。 为这 15 个任务各写一套第三方中立轨迹：由不知道提交内容的人（或直接用标注者的 oracle 轨迹）按规格里的演示场景编写，覆盖核心循环、内容变化、终局状态。
  • 测量。 用同一验证器与同一 rubric，分别在「agent 自带轨迹」与「第三方轨迹」下重跑，报每个 agent 的四维分与总分，以及两种条件下的排名。
  • 判据。 若两种条件下总分的秩相关高（例如 Spearman >0.9）且分差在裁判噪声（论文实测标准差约 0.004）的几倍以内，则轨迹自证的偏差可以忽略，benchmark 的排名可信；若排名发生翻转，或某个 agent 的分数变化超过它与相邻 agent 的间距，则说明当前分数是「造游戏 + 演游戏」的合成量，必须拆开报告。这一实验一周内可完成，且不需要重新运行任何 agent。

§ 11 — 最强反例设计 ​

站在反对者立场，最有力的一击是构造一个得高分的非游戏，证明分数可以与可玩性脱钩。

做法：手工做一个 Godot 工程，标题界面精美、有完整的过场演出、有一屏做工考究的 UI 与美术资源（直接用挂载的 Kenney / OpenGameArt 素材），但核心循环是空的——按键不改变任何状态，敌人是静态贴图，胜负条件不可达。然后为它录三条轨迹：一条只走标题到过场，一条展示一屏「内容目录」式的界面（多个单位、多张卡牌、多个关卡缩略图，全是静态展示），一条在结算界面停留。由于 Art and Presentation 与 Content Depth 合计占 0.70、且这两类里不少条目适合 max 聚合，这个「漂亮的非游戏」很可能拿到不低的分数，而它连一个动作—反应回路都没有。把它的得分与 Opus-4.7 的 41.46% 放在一起，就直接量化了权重设计与 max 聚合共同造成的可游戏化空间。

第二类替代解释针对裁判。人工校准只覆盖三个任务族、样本小、作者自己声明「不用于估计标注者一致性」，而观察到的偏差是分维度有方向的（人类在 D 与 A 上更严），偏偏 D 与 A 是权重最高的两项。把裁判换成另一个家族的多模态模型（例如换成非 GPT 系）重跑全部 140 个任务，如果 agent 排名发生变化，那么「Opus-4.7 领先 GPT-5.5 约两个点」这一结论就落在裁判选择的噪声里——尤其考虑到裁判本身就是 GPT-5.5，与被测配置之一同源。

§ 12 — Follow-up Research Idea ​

把验证从「被测系统自证」改成对抗式的证伪博弈。

(a) 驱动它的局限。 当前设计在两个坏选项之间做了取舍：验证器自主探索会引入策略依赖的方差，agent 自带轨迹会引入自证偏差。作者选了后者，并用隐藏 rubric 与 oracle 校验来缓解。但两个选项其实共享同一个隐含前提——只有一方在决定「怎么玩」。

(b) 可借鉴的邻域工具。 交互式证明系统与 debate 式对齐。引入第二个 prover agent，它只看得到公开规格与提交的工程（看不到 rubric），任务是构造证伪轨迹：找出规格中承诺过、但实际游玩中不成立的行为。builder 交的是展示证据，prover 交的是反证据，两组证据一起送进裁判，rubric 条目按「正向证据 − 反证据」结算。这把游戏评测变成一个零和的证据博弈，自证偏差被对手的激励直接抵消；同时它天然产出可解释的失败报告，而不只是一个百分数。

(c) 第一个实验长什么样。 先做最小版本：对现有 140 个提交，给一个独立的 GPT-5.5 prover 配置公开规格 + 工程源码 + 有限的探索预算（例如 30 次截图与 10 条候选轨迹），让它专门去找「规格说有、玩起来没有」的条目。裁判对每条 rubric 同时看 builder 与 prover 的证据。检验两件事：其一，prover 能否稳定地把「漂亮的非游戏」压到低分（§11 那个人造样本正好可以当作 sanity check）；其二，加入 prover 后 agent 排名相对纯自证条件变化多大——变化越大，说明当前 benchmark 的自证偏差越不可忽视，也就越支持把对抗验证做成标准配置。
