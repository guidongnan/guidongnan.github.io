VidProM: A Million-scale Real Prompt-Gallery Dataset for Text-to-Video Diffusion Models ​

项内容
arXiv2403.06098
提交日期2024-03-10（v4 修订于 2024-09-30）
作者Wenhao Wang（University of Technology Sydney）, Yi Yang（Zhejiang University）
分类cs.CV, cs.CL（NeurIPS 2024 Datasets and Benchmarks Track）
一句话从 Pika 官方 Discord 的 10 个频道抓下 8 个月的真实用户交互，清出 1,672,243 条去重的文生视频 prompt，再花约 50,631 个 V100 GPU 小时用三个开源模型补跑，凑成 669 万条视频，每条 prompt 附带 UUID、时间戳、六项 NSFW 概率与 3072 维 embedding。

所属教程：后训练与强化学习

版本与数字口径

本文按 v4（2024-09-30）的 HTML 全文撰写。需要说明：正文 Table 1（VidProM 与 DiffusionDB 的基本信息对照）在 arXiv HTML 渲染中数值单元格为空，因此下文只引用正文文字里明确写出的对照量（如 "+40.6% 语义唯一 prompt"、"平均每来源重复率 1 对约 8.2"、token 上限 8192 对 77、时间跨度 8 个月对 1 个月）。附录 C、D 的表格数值渲染完整，可直接引用。

§ 1 — 研究问题与重要性 ​

2024 年初 Sora 的公开让文生视频从"能不能做"变成"怎么用好"。而"用好"的第一入口是 prompt。文生图领域早就有 DiffusionDB 这样的 prompt-gallery 数据集，支撑了 prompt engineering、生成内容检测、模型评测一整批研究；文生视频这边则完全空白——没有人知道真实用户对着视频模型到底写什么。

这个空白不只是"少一份数据"。它导致三类问题都无法被研究。第一，评测不真实：VBench、EvalCrafter、FETV 这些 benchmark 用的都是研究者精心设计的小规模 prompt，模型在这些 prompt 上的表现与它在真实用户手里的表现是两回事。第二，训练分布与使用分布错位：现有模型都在 caption-真实视频对上训练（WebVid-10M、HDVILA-100M、Panda-70M），而 caption 是别人对已有视频的描述，prompt 是用户对不存在的视频的想象，两者的语言分布不同。第三，安全研究没有素材：伪造视频检测、扩散模型的视频复制检测都需要大批量的模型生成视频，而这些视频过去不存在公开集合。

VidProM 的定位是把这三件事一次性打开：提供 prompt、提供对应的生成视频、并用附录里的三个实证研究说明它们各自能支撑什么。

§ 2 — 前人工作与不足 ​

文本-视频数据集（WebVid-10M、HDVILA-100M、Panda-70M、MSR-VTT、InternVid、CelebV-Text）：这些是 caption-（真实）视频对，不是 prompt-（生成）视频对。它们的用途是训练，不是研究用户想生成什么。论文在附录 B 直接量化了这个差距：从 Panda-70M 随机取 160 万条 caption 与 VidProM 一起做 WizMap 可视化，两者分布显著不同。作者举的例子很具体——用户想生成城市夜景或蜘蛛侠这类内容，而训练数据里这类视频很少甚至没有；另一方面用户常以 "Generate a video of" 开头、以 "4K" 结尾，这些词在训练 caption 里不出现。

Prompt 数据集（PromptSource、DiffusionDB）：PromptSource 是文本到文本的，DiffusionDB 是文本到图像的。DiffusionDB 拿了 ACL 2023 最佳论文提名，证明了这类数据集的价值，但它的三处局限直接定义了 VidProM 的设计空间：用 OpenAI-CLIP 做 embedding（上限 77 token）、只采集了 1 个月（2022 年 8 月）、图像全部来自 Stable Diffusion 一个模型（平均每来源重复率约 8.2）。

文生视频模型（Pika、Text2Video-Zero、VideoCrafter2、ModelScope、Sora、SVD、VideoPoet 等）：论文选了四个"公开可访问"（能拿到生成视频或预训练权重）的作为视频来源。

作者对 DiffusionDB 的批评落在一个具体的技术点上：文生视频的 prompt 显著更长更复杂，77 token 的 CLIP 编码器根本装不下。

§ 3 — 重建作者的思考路径 ​

第一个问题是数据从哪儿来。真实用户的文生视频交互在 2023 年只有一个大规模公开场所：Pika Labs 的 Discord 服务器，用户在频道里对 bot 发 prompt，bot 回视频。而 Pika 的服务条款第 4.5.a 条明确写着用户授予其他用户 CC BY-NC 4.0 许可——这是整个数据集能合法开源的法律前提，作者把它写进了正文。

第二个问题是抓下来之后怎么清。原始 HTML 里混着图生视频的请求（对应的图不公开，没法用）、以及有 prompt 无视频的记录（可能被 Pika 封禁或被用户隐藏）。这两类必须去掉。再去重，得到 1,672,243 条。

第三个问题是：只有 Pika 一个来源的视频，会重蹈 DiffusionDB "单模型"的覆辙。解决办法是本地补跑——但这很贵。作者选了三个开源模型（VideoCraft2、Text2Video-Zero、ModelScope）跑完全部 167 万条 prompt，代价是 10 台服务器 × 8 张 V100、约 50,631 GPU 小时。这是本文最重的工程投入，也是它相对 DiffusionDB "只爬不生成"的核心差异。

第四个问题是"唯一性"的定义。字符串去重太弱——"a cat sitting" 和 "a cat is sitting" 会被算成两条。作者引入了语义唯一：任意两条 prompt 的 embedding 余弦相似度小于 0.8。这需要算一个 1,672,243×1,672,243 的相似度矩阵，用 Faiss 分布到 8 张 A100 与 128 个 CPU 核上，耗时约 0.604 小时。得到 VidProS 子集，1,038,805 条。

§ 4 — 核心 Intuition ​

用户对视频模型写的 prompt，与用户对图像模型写的 prompt，是两种不同的语言：前者必须描述时间维度（动作变化、场景切换）、动态行为（飞、工作、写字）和时长（"很久"、"1 分钟"），因此系统性地更长更复杂。既然语言不同，那么在文生图 prompt 上做出来的一切结论（prompt engineering 的技巧、embedding 的选择、评测集的构造）都不能直接搬过来，必须重新采一份数据。而采这份数据的唯一现实途径，是去真实用户已经在用的地方（Pika 的 Discord）把交互日志捞出来。

§ 5 — 具体方法与完整 Pipeline ​

一个数据点长什么样：一条 prompt、一个 UUID、一个时间戳、六项 NSFW 概率、一个 3072 维 prompt embedding、四个生成视频。

收集源 HTML。用 DiscordChatExporter 抓 Pika 官方 Discord 中 10 个频道在 2023 年 7 月至 2024 年 2 月之间的聊天消息，存成 HTML。

抽取与嵌入。用正则从 HTML 里提取 prompt 与时间戳；过滤掉图生视频的 prompt 与无关联视频的 prompt；去重并分配 UUID，得到 1,672,243 条唯一 prompt。因为文生视频 prompt 显著更长，用 OpenAI 的 text-embedding-3-large（支持 8192 token）做嵌入，保留原始 3072 维输出，让使用者自行降维。

NSFW 概率。Pika 的频道本身禁止 NSFW 内容并会自动拒绝有害 prompt，但仍有漏网的。作者用 Detoxify 给每条 prompt 打六个维度的概率：toxicity、obscenity、identity attack、insult、threat、sexual explicitness。结果是不到 0.5% 的 prompt 在某个维度上概率超过 0.2。给六个分数而不是一个二值标签，是为了让使用者自己按任务设阈值。

抓取与生成视频。Pika 视频从提取到的链接直接爬；另外三个模型本地生成。总计 6.69 million = 4 × 1,672,243 条视频，总时长 14,381,289.8 秒。各模型的视频长度：Pika 3.0 秒、VideoCraft2 1.6 秒、Text2Video-Zero 2.0 秒、ModelScope 2.0 秒。

语义去重（附录 A）。算相似度矩阵 S=E×ET，把相似度超过阈值 θ=0.8 的对收进 Psimilar​，再据此筛出语义唯一集合，得到 VidProS 的 1,038,805 条。

§ 6 — 核心数学推导 ​

本文的形式化内容只有语义去重那一处，且更接近工程实现而非推导：给定 N=1,672,243 条归一化 embedding 组成的矩阵 E∈RN×d（d=3072），计算 S=EET，对所有 i<j 保留 Sij​>θ 的对，然后按贪心策略剔除冲突项。

有两点值得点出来。第一，完整的 S 有约 2.8×1012 个元素，直接存下来不现实，所以必须用 Faiss 做分块近邻检索——0.604 小时这个数字只有在这个前提下才成立。第二，也是更重要的一点："任意两条相似度 < 0.8" 这个定义与贪心剔除并不严格等价。贪心过程依赖遍历顺序，不同顺序会得到不同大小的保留集合；要真正得到最大的满足条件的子集，等价于在"相似度超阈"图上求最大独立集，这是 NP-hard 的。所以 1,038,805 这个数字应理解为某个贪心解的大小，而不是"语义唯一 prompt 的真实数量"。论文没有讨论这一点，但它影响到 "+40.6% 相对 DiffusionDB" 这个核心对照的可比性——除非两边用了完全相同的遍历顺序策略（作者说明对 DiffusionDB 用同一个 text-embedding-3-large 重新嵌入，但没说去重顺序）。

§ 7 — 实验设计与结论 ​

本文的"实验"分两类：一类论证数据集的必要性，一类演示它能支撑什么研究。

问题一：文生视频 prompt 真的和文生图 prompt 不一样吗？ 三条证据。语义上，作者指出三处系统差异——时间维度（"动作变化"、"场景转换"）、动态描述（飞、工作、写字，而文生图更关注静态外观）、时长（"很久"、"1 分钟"）。长度上，VidProM 中超过 70 词的 prompt 接近 60,000 条，DiffusionDB 只有约 15,000 条；超过 100 词的 VidProM 有超过 25,000 条，DiffusionDB 接近 0。作者还拿 Sora 官方例子做参照：'Tokyo Girl' 的 prompt 有 64 词，OpenAI 官网上最长的 prompt 有 95 词。分布上，各随机取 10,000 条做 t-SNE，两者几乎线性可分；用 WizMap 看全量主题，两群人都关心汽车、食物、可爱动物，但文生图用户偏向艺术画作、文生视频用户几乎不碰这块，反而更倾向生成走路这类日常人类活动。

问题二：规模与多样性上相对 DiffusionDB 如何？ 唯一 prompt 总数两者接近，但 VidProM 的语义唯一 prompt 多 40.6%。采集时间跨度 8 个月对 1 个月。嵌入模型 token 上限 8192 对 77。平均每来源重复率 1 对 约 8.2——这里要诚实地读：VidProM 的"1"是因为每个 prompt 在每个模型上只跑一次，这是设计的直接结果而非涌现的多样性性质，把它与 DiffusionDB 的 8.2 并列比较，说服力弱于其他几项。

问题三：现有伪造图检测器能直接用到伪造视频上吗？ 附录 C 给了明确的否定答案。从四个模型各随机取 10,000 条生成视频作为假样本，从 DVSC2023 取 10,000 条真实视频作为真样本，因为没有检测器能直接吃整段视频，统一抽中间帧。八个开源 SOTA 检测器的平均准确率（随机基线是 50）：CNNSpot 50.41、FreDect 60.98、Fusing 50.44、Gram-Net 63.64、LGrad 51.69、LNP 45.32、DIRE 49.44、UnivFD 51.27。平均 mAP：CNNSpot 46.82、FreDect 60.99、Fusing 48.97、Gram-Net 69.08、LGrad 52.73、LNP 43.70、DIRE 48.20、UnivFD 52.55。八个里有五个准确率在 50±2 之内，LNP 甚至低于随机。作者的解读也很到位：专为扩散过程设计的 DIRE、号称跨生成模型泛化的 UnivFD 都失败了，反而依赖传统线索的方法最有效——Gram-Net 用全局纹理统计、FreDect 用频域分析。

问题四：扩散模型生成的视频会复制训练内容吗？ 附录 D。从 VideoCraft2 与 ModelScope 的训练来源里随机取 100 万条视频作参考库，用作者自己此前在 DVSC2023 上夺冠的 FCPL 做视频复制检测。定量结论：复制确实发生但比例很低，Text2Video-Zero 约 2% 的生成视频最大归一化分数大于 0（复制率最高），商业模型 Pika 最低，作者推测是商业模型做了防复制措施以规避法律风险。定性上给了一个有力的例子：Pika 生成的视频高度复制了达利的《记忆的永恒》，该画版权属于 Gala-Salvador Dalí Foundation。作者同时诚实标注了两处局限：参考库只用了部分训练来源，会低估复制率；现有复制检测模型只在人工变换（水平翻转、随机裁剪）上训练，对扩散模型产生的复制模式泛化不佳，附录 D.3 展示了明显是复制但分数低于 0 的失败案例。

问题五：数据集能直接训出什么？ §6 演示了自动 prompt 补全：把它当作通用文本生成任务，用 HuggingFace 的 run_clm.py，用 DeepSpeed 在 8 张 A100 上微调 Mistral-7B-v0.1，2 小时完成。示例输出（如 "A cat sitting" → "A cat sitting on a desk, typing on its laptop..."）里出现了明显的拼写损坏（"wm glow"、"discded items"、"weing glasses"、"chacte"），作者原样展示未作评论——这些应是训练数据本身携带的用户拼写噪声。

顺带的效率数字：在单张 V100 上，ModelScope 生成一条视频需 43 秒，VideoCrafter2 需 51 秒。这两个数支撑了作者提出的"检索已有视频重建而非从噪声生成"这一效率研究方向。

§ 8 — Take-aways ​

5 句话版：文生视频领域此前没有任何公开的真实用户 prompt 数据集，导致评测、训练分布分析与生成内容安全三类研究都缺素材。VidProM 从 Pika 官方 Discord 的 10 个频道抓下 8 个月交互，清出 1,672,243 条唯一 prompt 与 669 万条视频（Pika 爬取 + 三个开源模型本地生成，约 50,631 V100 GPU 小时）。相对 DiffusionDB，它的语义唯一 prompt 多 40.6%，用 8192-token 的 text-embedding-3-large 取代 77-token 的 CLIP，采集跨度 8 个月对 1 个月，且长 prompt 数量高一个量级。三个附录实证给出了这份数据最有价值的部分：现有伪造图检测器迁移到伪造视频上八个里五个接近随机、一个低于随机；扩散模型确实会复制训练视频（Text2Video-Zero 约 2%，商业模型 Pika 最低）；训练 caption 与用户 prompt 的分布显著错位。数据与代码以 CC BY-NC 4.0 公开。

3 句话版：文生视频的 prompt 因为要描述时间、动态与时长而系统性地比文生图 prompt 更长更复杂，所以文生图的 prompt 数据集不能替代它。VidProM 用真实 Discord 日志加上五万 GPU 小时的补跑，把这份数据以及对应的四模型生成视频一次性开源。它最硬的贡献不是规模，而是附录里那两组阴性结果——伪造视频检测和扩散复制检测这两条现有技术路线在真实数据上都不成立。

1 句话版：把真实用户与商业文生视频模型的八个月交互变成一份带 embedding、NSFW 概率与四模型生成视频的公开数据集，并用它证明现有伪造检测与复制检测方法在视频上基本失效。

§ 9 — 最脆弱的假设 ​

失败代价最大的假设是：Pika Discord 上的 prompt 能代表"真实用户的文生视频意图"。数据集的全部价值主张——"更真实的评测"、"训练分布与使用分布的错位"、"prompt engineering 的素材"——都建立在这个代表性上。如果它只代表"2023 年下半年愿意泡在 Discord 里用免费额度的一小群人"，那么在它上面得出的所有分布结论都是局部的。

有三条具体理由让人怀疑它不成立。第一，单一产品单一渠道。Pika 有自己的模型能力边界、自己的 prompt 语法习惯、自己的社区文化。作者花了大力气用四个模型生成视频来避免"单一模型"的问题，却没有对"单一 prompt 来源"施加同等的警惕——而后者恰恰是数据集的核心资产。DiffusionDB 被批评"图全来自 Stable Diffusion"，VidProM 的 prompt 则全来自 Pika 用户，这是同构的问题。第二，Discord 用户是自选样本。愿意在公开频道里生成视频的人，与用付费 API 的商业用户、与用本地开源模型的研究者，写 prompt 的方式很可能不同。第三，采集窗口正好覆盖 Sora 发布前后（2023 年 7 月至 2024 年 2 月），这段时间用户对视频模型能力的预期在快速变化，prompt 的分布本身可能是非平稳的——数据集带了时间戳，完全可以做这个分析，但论文没做。

论文对这个假设没有提供任何直接证据。它做的所有对照都是 VidProM vs DiffusionDB（跨模态）或 VidProM vs Panda-70M（prompt vs caption），没有一处是 VidProM vs 另一个来源的文生视频 prompt——因为当时确实没有第二个来源。这是一个可以理解的困境，但论文把"第一份"直接当成了"有代表性"，中间那一步论证是缺失的。

还有一处更容易被忽略的内部矛盾值得记下来：附录 E 的 datasheet 在"数据集中是否存在错误、噪声或冗余"一栏回答 "No. All videos and prompts are extracted as is from the Discord chat log." 这与论文自己的三处内容直接冲突——正文承认 VidProM 仍包含未被 Pika 过滤掉的 NSFW prompt；§3 报告 167 万条 prompt 里有 63 万余条不是语义唯一的（1,672,243 − 1,038,805 = 633,438），这按任何合理定义都是冗余；§6 展示的模型输出里带有大量拼写损坏，说明源数据有噪声。"as is" 说明的是未做处理，不等于不存在噪声，datasheet 把这两件事混为一谈了。

§ 10 — 最小复现实验 ​

一周内可做，不需要任何视频生成，只用公开的 VidProM 元数据（prompt + 时间戳 + embedding，无需下载 6.69M 视频）。目标是检验 §9 的代表性假设中最可检验的一支：分布是否随时间漂移。

数据：VidProM 的 prompt 与时间戳（HuggingFace 上有 10,000 条示例子集可先跑通流程，再拉全量元数据）。

实现：按月把 167 万条 prompt 切成 8 个桶（2023-07 至 2024-02）。对每个桶计算三组统计量：(a) 词数分布的中位数与 90 分位；(b) 用现成 embedding 算桶内平均两两余弦相似度（作为主题集中度的代理）；(c) 桶间的分布距离——用每个桶随机采样 2 万条 embedding，算两两桶之间的 MMD 或 Fréchet 距离。

测量：一张 8×8 的桶间距离矩阵，加上三条随时间变化的曲线。

判据：如果桶间距离矩阵在 2024-02（Sora 发布月）那一行/列明显跳变，或者词数中位数在这八个月里单调显著上升，就说明 prompt 分布是非平稳的，"VidProM 代表真实用户意图"这个静态论断需要改写成带时间范围的版本。作为对照，同样的分析可以在 DiffusionDB 上做——但它只有 1 个月，正好说明为什么这个检验只有在 VidProM 上才做得成。这个实验的成本几乎为零，而它能把论文最核心的假设从"未验证"推进到"部分验证"。

§ 11 — 最强反例设计 ​

最有力的攻击针对附录 C 那组伪造视频检测的阴性结果，因为它是全文最强的实证发现，也最容易被一个替代解释推翻。

论文的结论是"现有伪造图检测器无法泛化到伪造视频"。但实验设计里有一个混杂变量：真样本来自 DVSC2023，假样本来自四个文生视频模型。这两组视频在分辨率、编码方式、时长、内容主题上都不同。一个检测器在这个设定下接近随机，可能不是因为"检测不出扩散痕迹"，而是因为它学到的是训练时那批真实照片的低层统计特征，而 DVSC2023 的视频帧（多为网络视频，经过多轮转码压缩）与之相差太远——也就是说，检测器在真样本这一侧就已经失效了。

区分实验：把假样本换成同一批真实视频经过一次文生视频模型的图生视频重建（或者退一步，把真实视频帧过一遍 SD 的 VAE 编解码），这样真假两侧的分辨率、编码、内容全部对齐，唯一差别是有没有生成模型的痕迹。如果在这个受控设定下八个检测器的准确率大幅上升，那么论文的结论要弱化为"跨域偏移让现有检测器失效"，而不是"扩散视频的痕迹检测不出来"。如果准确率仍在 50 附近，论文的结论就被显著加强。目前的证据无法区分这两种情况，而论文里有一条线索是指向替代解释的：表现最好的两个方法（Gram-Net 用全局纹理统计、FreDect 用频域分析）恰恰是对编码/压缩差异最敏感的两类方法——这与"它们真的捕捉到了生成痕迹"同样吻合，也与"它们捕捉到了域差异"同样吻合。

第二种攻击针对复制检测那一节。论文用 FCPL（作者自己的方法）在 100 万条参考视频上检索，报出 Text2Video-Zero 约 2% 的复制率，同时承认参考库不完整会低估、且检测模型对扩散式复制泛化不佳（附录 D.3 有失败案例）。把这两条局限放在一起，2% 这个数字实际上是一个下界的下界，不应被引用为"复制现象很罕见"的证据。一个能证伪"复制罕见"的实验是：不做全库检索，而是针对性地用 VidProM 里那些明确点名版权作品的 prompt（"The Persistence of Memory"、"Spiderman" 这类，论文自己的例子和 §6 的生成示例都表明这类 prompt 大量存在）去检索，看条件复制率是多少。如果在这个子集上复制率是两位数，那么"复制只占极小比例"的整体结论就会被重新框定成"整体稀疏但在版权敏感 prompt 上高度集中"——这对法律风险评估是完全不同的结论。

§ 12 — Follow-up Research Idea ​

驱动它的局限：本文把 prompt、视频、NSFW 概率、embedding 打包发布，但整个数据集是无标签的——没有人告诉你哪条 prompt 得到了用户满意的视频。而 Discord 交互里其实埋着这个信号：用户对 bot 返回的视频会做出反应（重新生成、微调 prompt 后重发、或者就此停止）。论文在提取阶段把这些行为线索连同"无关联视频的 prompt"一起丢掉了。

新的 framing：不把 Discord 日志当作 prompt 的仓库，而当作隐式偏好数据的仓库。文生图领域的偏好数据必须靠专门做一个应用（Pick-a-Pic，见 2305.01569）或雇标注者（HPD v2，见 2306.09341）来收集，成本很高；而"用户改了 prompt 又发一次"这个行为，本身就是对上一个结果的负面判断。用户连续发出的 prompt 序列 p1​→p2​→⋯→pk​（然后停止）给出的信号是：pk​ 对应的视频比前面的都令人满意。这把一个纯 prompt 数据集变成了一个百万级的隐式偏好数据集，而且完全免费。

可借鉴的相邻领域工具：信息检索里的 click model 与 session-based implicit feedback 有整套成熟方法处理"如何从行为序列里推断满意度"，包括位置偏置、放弃偏置、以及"用户离开是因为满意还是因为放弃"这个经典的歧义（对应到这里就是：用户不再改 prompt，可能是拿到了想要的，也可能是放弃了）。IR 领域用 A/B 实验校准 click model 的做法，可以直接搬来做校准。

第一个实验长什么样：先做校准，这一步不能省。从 Discord 日志里恢复出 session 结构（同一用户在短时间窗内的连续 prompt），随机采样 1,000 个 session，人工标注每个 session 的终止原因是"满意"还是"放弃"——这是把行为信号变成偏好信号的地基，没有它后面的一切都是猜测。然后在校准好的子集上训练一个简单的满意度预测器，用它给全量 session 打标，构造出 (pk​ 的视频,pk−1​ 的视频) 的偏好对。最后的检验是：用这份隐式偏好数据训一个视频版的打分器，在一个独立收集的小规模人工标注视频偏好集上评它的准确率，与两个基线比较——随机（50），以及"逐帧跑 HPS v2 取平均"这个不需要任何新数据的平凡基线。如果赢不过后者，说明 Discord 的行为信号里没有帧级美学之外的额外信息，这条路就到此为止；如果赢了，那么文生视频的偏好对齐就有了一个不需要新标注预算的数据来源。
