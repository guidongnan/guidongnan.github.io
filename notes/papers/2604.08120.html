Small Vision-Language Models are Smart Compressors for Long Video Understanding ​

项内容
arXiv2604.08120
提交日期2026-04-09
作者Junjie Fei, Jun Chen, Zechun Liu, Yunyang Xiong, Chong Zhou, Wei Wen, Junlin Han, Mingchen Zhuge, Saksham Suri, Qi Qian, Shuming Liu, Lemeng Wu, Raghuraman Krishnamoorthi, Vikas Chandra, Mohamed Elhoseiny, Chenchen Zhu
分类cs.AI, cs.CL, cs.CV, cs.LG
一句话用一个 2B 小 VLM 当局部时序压缩器，把问题前置到压缩之前做跨模态蒸馏，产出定长 memory token；推理时再用同一次前向里顺手取出的 Yes/No logit 差当相关性先验，按段分配 token 预算并用头部截断落地。

所属教程：长视频理解

本页依据 arxiv.org/e-print/2604.08120 取回的 LaTeX 源码撰写。方法在正文中名为 Tempo，分配机制名为 ATA（Adaptive Token Allocation）。

§ 1 — 研究问题与重要性 ​

把 MLLM 推到小时级视频上，卡点是结构性的：视频的连续视觉流是无界的，下游 LLM 的上下文窗口是有界的。时长一长，原始视觉 token 就把输入容量吃穿，注意力被稀释，模型在长上下文里找不到稀疏证据，也就是 lost-in-the-middle。

现有做法要么稀疏采帧（省算力但可能跳过决定性瞬间），要么保留更多帧再做查询无关的压缩（均匀时空池化、token merging）。后者的问题在于：在不知道用户会问什么的情况下压缩，必然在关键片段上抹掉细粒度证据，同时把带宽浪费在无关背景上。即便是较早的查询感知方法（如 LongVU）也依赖一个独立的辅助特征匹配模块，把路由机制与端到端的多模态流水线割开了。

本文的立场是把 token 压缩当成一次早期跨模态语义蒸馏：在压缩发生之前就把查询喂进去，让压缩器直接产出与用户意图对齐的表示。

§ 2 — 前人工作与不足 ​

视频 MLLM 主流范式（VideoChat2、VILA、LLaVA-OneVision、VITA-1.5、Kimi-VL、InternVL3.5、Molmo2、Qwen-VL 系列）把采样帧直接映射进 LLM 上下文，短视频上很强，但把这种稠密表示推到小时级会导致 token 线性爆炸。

上下文扩展这一支（LongVA 的窗口外推、LongVILA 的序列并行、LongLLaVA 的 Mamba-Transformer 混合架构）保住了视觉保真度，代价是仍然要吞下稠密视觉流，单条视频几十万 token 的显存开销让常规推理不现实。

查询无关的 token 削减这一支（受 FastV、ToMe 启发，代表如 VideoChat-Flash 的分层压缩、Storm 的时空池化）成本低，但因为完全不知道问题是什么，会模糊语义边界、丢掉短暂但关键的片段。

分层与查询感知架构（SlowFast-LLaVA、LLaVA-Video$_{slowfast}$、Keye-VL-1.5、BIMBA、LongVU）已经在往对的方向走，但它们的资源分配要么纯由视觉驱动（帧间相似度），要么依赖与端到端解码解耦的外挂模块。

§ 3 — 重建作者的思考路径 ​

第一个观察：如果压缩必须发生，那它发生在"看到问题之前"还是"之后"是一个纯粹的架构选择，而不是物理约束。把查询前置到压缩器输入里，压缩就从一个视觉操作变成一个跨模态操作，这一步几乎不增加成本。

第二个观察：谁来当压缩器。用大 LLM 本身太贵，用一个专门训练的编码器又要从头设计。而现成的小 VLM（2B 级）已经具备相当的跨模态对齐能力，把它当成"局部时序压缩器"，让它把一个 8 帧片段连同查询压成固定条数的 memory token，是一个成本可控的选择。因果注意力保证放在序列末尾的 memory token 能看到前面所有视觉与文本内容。

第三个观察：预算怎么硬性满足。训练时用定长 kmax​ 是稳定的，但推理时不同视频段数不同，必须能按段分配。作者注意到同一个小 VLM 的前向里已经藏着一个可用的相关性信号——只要在压缩指令后追加一句二元指令，取模型在给出 Yes/No 之前的隐状态、用词表里 Yes 与 No 两个 token 的 LM head 权重差做投影，就能拿到一个连续的相关性分数，且不需要自回归解码。这样路由信号与压缩表示来自完全相同的多模态上下文。

第四个观察：拿到每段预算之后怎么截。作者的消融发现因果注意力下语义天然向前堆积，于是最简单的头部切片就够，不必做有 O(N2) 开销的空间聚类。

§ 4 — 核心 Intuition ​

压缩器只要在压缩之前先读到问题，它产出的定长表示就已经是意图对齐的；而这个压缩器在同一次前向里还免费给出了"这一段跟问题有没有关系"的判断。于是"压多少"和"压什么"两个决策共享一次计算，都不需要额外的路由网络。

§ 5 — 具体方法与完整 Pipeline ​

架构。局部压缩器 Cϕ​ 从 Qwen3-VL-2B-Instruct 初始化，全局解码器 Dθ​ 用 Qwen3-LM-4B，中间一个线性 projector，合计 6B。视频用 Decord 按 2 FPS 抽帧，超限则均匀下采。训练时按 4 帧一段，推理时窗口扩到 8 帧。

压缩过程。对每段 Si​，小 VLM 构造一条因果序列：系统提示、视觉 token Xi​、用户查询 Q、可学习 memory token M。把 M 放在最后是关键，因果注意力让每个 memory token 都能看到前面所有视觉与文本上下文，从而把与查询对齐的证据蒸馏进去。取最后一层隐状态得 Hi​∈Rkmax​×ds​，kmax​=128。组装全局序列时给每段前置一个显式文本时间戳（如 <t=2.0s>），作者称这显著稳定了下游 LLM 的长程归因。

训练。没有任何辅助压缩损失、路由网络或 token 丢弃正则，只用标准自回归目标 LAR​。定长 kmax​ 本身就是硬性的结构瓶颈，梯度自然逼着压缩器丢背景、留证据。课程分四阶段：Stage 0 冻结两端只训 projector（LCS-558K）；Stage 1 全解冻，约 2M 图像 + 1.38M 视频 + 143K 纯文本，视频稀疏采 8 帧；Stage 2 广泛 SFT，约 0.93M 图像 + 2.25M 视频 + 71K 文本，最大帧数上限 128；Stage 3 长上下文 SFT，冻结小 VLM 只微调全局 LLM，用 Stage 2 的 384K 高质量子集，帧数上限提到 384。训练在 64 卡集群上用 FSDP。数据配比主要沿用 VideoChat-Flash 与 LLaVA-OneVision-1.5，全部公开。

零样本相关性先验。在训练用的系统提示后追加一句严格的二元指令："Now, before compressing, answer exactly 'Yes' or 'No': is this segment relevant to the Query?" 取二元回答前一刻的隐状态 hirel​，用冻结的 LM head 中 Yes 与 No 两个词的权重做投影：

si​=σ((wyes​−wno​)⊤hirel​)∈(0,1).

推理时在同一次前向里截取该隐状态算分，再继续前向取 Hi​，因此路由与压缩严格条件于完全相同的上下文。

ATA 两阶段分配。先 Min-Max 归一化 s^i​，再线性映射到理想容量 kiideal​=kmin​+⌊(kmax​−kmin​)⋅s^i​⌋。若 ∑i​kiideal​≤Bmax​ 就直接采用以最大化稀疏度；否则以 Bbase​=N⋅kmin​ 保底、把残余预算 Bres​=Bmax​−Bbase​ 按归一化分数比例分下去。最后按 HiATA​=Hi​[1:ki​] 做头部切片。kmin​=4，即最不相关的段也保留 4 个 token 作为时间锚。

一个具体例子。问"讲座里演示者第二次切换幻灯片时屏幕上是什么"，1024 帧按 8 帧一段共 128 段。切幻灯片那两段的 si​ 接近 1，拿到接近 128 的 token；其余段落 si​ 低，被压到 4 个 token，只维持"这段时间在讲课"这条时间线，全局序列总量卡在 8K 以内。

§ 6 — 核心数学推导 ​

端到端目标就是标准的自回归似然，没有额外正则：

LAR​(θ,ϕ)=−t=1∑T​logpθ​(at​∣a<t​,Q,{H~i​}i=1N​).

值得单独说的是相关性分数的形式。(wyes​−wno​)⊤h 正是模型在该位置输出 Yes 与 No 两个 token 的 logit 之差；对它取 sigmoid，得到的就是在"只允许 Yes/No 两个候选"这一约束下 Yes 的条件概率。这个量是 O(1) 的一次向量内积，不需要采样、不需要解码，也不引入任何新参数——它复用的是冻结的 LM head 权重。

分配式子里两条分支的分界是 ∑i​kiideal​ 与 Bmax​ 的比较。当段数 N 很大时，保底项 N⋅kmin​ 会先把预算吃掉一大块，残余 Bres​ 变小，高相关段能拿到的增量随之压缩。这解释了论文在扫描分析中观察到的现象：在 2K/4K 这类紧预算下把 fmax​ 推得太高反而变差，因为时间锚提前耗尽了容量。

§ 7 — 实验设计与结论 ​

第一个问题：6B 模型在长视频上能到什么位置。 表 tab:main_table 覆盖 LongVideoBench(473s) / MLVU(651s) / Video-MME(1010s 与 Long 2386s) / LVBench(4101s)，并同时报告"每帧 token 数"与实测平均值。Tempo(4K 预算) 64.5 / 75.6 / 67.8 / 57.8 / 52.7，实测每帧 token 分别为 2.8 / 2.8 / 3.6 / 3.4 / 2.9；Tempo(8K 预算) 65.1 / 75.2 / 67.7 / 57.0 / 52.3，实测 3.1 / 3.3 / 4.3 / 4.1 / 3.5。对照组：VideoChat-Flash(7B, 16 tok/frame) 64.7 / 74.7 / 65.3 / 55.4 / 48.2；GPT-4o 66.7 / 64.6 / 71.9 / 65.3 / 30.8；Gemini 1.5 Pro 64.0 / — / 75.0 / 67.4 / 33.1；Qwen3-VL-8B 78.1 / 71.4 / 58.0。

读法要小心：在 LVBench 上 Tempo(4K) 的 52.7 确实远超 GPT-4o 与 Gemini 1.5 Pro，但在 Video-MME 上两个专有模型（71.9 / 75.0）都高于 Tempo（67.8）。LVBench 的优势与时长强相关。

第二个问题："更小的预算反而更好"是真的吗。 4K 与 8K 的对比：LVBench 52.7 对 52.3，Video-MME Long 57.8 对 57.0，MLVU 75.6 对 75.2，只有 LongVideoBench 是 8K 更高（65.1 对 64.5）。作者把这解释为更严格的信息瓶颈过滤掉了背景干扰，缓解 lost-in-the-middle。

第三个问题：各组件贡献。 表 tab:ablation_main 统一在 8K 预算、2 FPS、最多 1024 帧下做，五组消融（列序为 LongVB / MLVU / Video-MME Overall / Video-MME Long / LVBench）。

A 训练课程：w/o Stage 3（16K 预算）61.4 / 67.2 / 66.1 / 56.3 / 47.3；w/o ATA（16K 预算）62.8 / 73.5 / 67.0 / 56.2 / 51.1；默认（8K）65.1 / 75.2 / 67.7 / 57.0 / 52.3。用一半预算超过 16K 无分配的版本。

B 段级预算分配：Uniform Subsampling 61.9 / 74.0 / 66.3 / 55.2 / 49.9；Random Drop 59.3 / 70.9 / 63.6 / 55.2 / 49.8；Adversarial Routing（只留最低分段）50.7 / 59.3 / 52.4 / 47.8 / 36.9；Hard Top-K 63.5 / 73.9 / 66.7 / 56.2 / 52.7；ATA 65.1 / 75.2 / 67.7 / 57.0 / 52.3。这组对照做得比同类工作扎实：均匀采样与随机丢弃这两条平凡基线都给了，对抗路由的崩塌（LongVB 65.1 → 50.7）也确实证明相关性分数不是噪声。相对均匀采样的绝对增益是 +3.2 / +1.2 / +1.4 / +1.8 / +2.4。

C 段内 token 削减：Uniform Tail Truncation 59.5 / 71.6 / 64.1 / 54.8 / 41.8；Uniform Head Truncation 63.2 / 73.4 / 66.9 / 56.2 / 51.5；Token Merging 63.6 / 74.9 / 66.3 / 55.4 / 53.0；Dynamic Tail 61.9 / 73.4 / 64.8 / 54.2 / 50.5；Dynamic Head（默认）65.1 / 75.2 / 67.7 / 57.0 / 52.3。头部截断稳定压过尾部截断，这是 semantic front-loading 的直接证据。

D 相关性来源：Base Model Prior(标准提示) 64.6 / 75.1 / 67.2 / 56.1 / 52.6；Base Model Prior(显式路由提示) 65.7 / 76.3 / 67.6 / 57.3 / 52.7；External Dense Retriever 64.3 / 75.4 / 67.2 / 57.0 / 51.8；Tempo SVLM Prior(标准提示) 64.1 / 75.4 / 67.2 / 57.0 / 53.4；Tempo SVLM Prior(显式路由提示，默认) 65.1 / 75.2 / 67.7 / 57.0 / 52.3。

E 时间连续性：Hard Pruning（无关段 0 token）63.9 / 74.8 / 67.4 / 56.3 / 52.3；kmin​=4 的最小时间锚 65.1 / 75.2 / 67.7 / 57.0 / 52.3。

第四个问题：帧数与预算怎么配。 扫描分析显示低帧数区各预算曲线重合（未压缩量本就低于阈值）；帧数上去后 2K/4K 这类紧预算会因时间锚提前耗尽容量而退化；标准长视频任务（Video-MME Long）在 4K 预算、fmax​=1024 处见顶，而极长的 LVBench 需要更大容量，8K/12K 下随帧数单调上升，在 fmax​=2048、$B_{\max}=12$K 处达到 53.7。

§ 8 — Take-aways ​

5 句版：把查询前置到压缩之前，token 削减就从视觉操作变成跨模态蒸馏，且不需要任何辅助损失——定长 memory token 本身就是硬瓶颈。同一次小 VLM 前向里的 Yes/No logit 差可以直接当相关性先验，路由与压缩因此严格共享上下文、零额外延迟。因果注意力导致语义向前堆积，头部截断稳定优于尾部截断（LongVideoBench 63.2 对 59.5、65.1 对 61.9），这是本文最干净的一条经验发现。给无关段保留 4 个 token 的时间锚比直接剪成 0 更好，说明长视频里"知道这段时间发生过什么"本身有价值。但消融 D 显示默认的 Tempo SVLM Prior 在五列里有四列不如 Base Model Prior + 显式路由提示，作者只用 Video-MME 那 0.1 点优势论证"综合性能更优"，这个归因站不住。

3 句版：Tempo 用 2B 小 VLM 当查询感知的局部压缩器，ATA 用零样本相关性先验按段分配 token 并做头部截断。6B 架构在 LVBench 4K 预算下拿到 52.7（实测每帧 2.9 token），扩到 2048 帧 / 12K 预算为 53.7。段级分配相对均匀采样的绝对增益是 1.2–3.2 点，随时长增大而放大。

1 句版：长视频真正需要的不是更大的上下文窗口，而是让一个便宜的压缩器在压缩之前就知道用户要问什么。

§ 9 — 最脆弱的假设 ​

失败代价最大的一条是：semantic front-loading——因果注意力下小 VLM 会把最重要的语义打包进最早生成的那几个 memory token，因此头部截断近似无损。 整个 ATA 的物理落地完全建立在这条假设上；如果它不成立，所有动态预算都失去意义，因为切下来的那 4 个或 16 个 token 未必是最有信息的。

论文为它提供的证据是消融 C 里头部截断对尾部截断的稳定优势。这个证据是真的，但它只证明了"头比尾好"，没有证明"头就是最好"。两者之间有一个未被排除的替代解释：memory token 的位置顺序可能主要编码的是段内时间顺序，而不是显著性排序。若是这样，头部截断实际上在做的事是"每段只看前几帧"——这正是长视频理解领域反复出现的一种平凡失败模式，而它在很多基准上恰好也能拿到不错的分数，因为事件往往在段的开头就已经交代清楚。

更关键的是训练与推理的错配。模型全程用定长 kmax​=128 训练，从未见过被截断的序列；front-loading 因此是一个没有被任何目标函数优化过的涌现性质。而 ATA 的动态范围要压到每帧 0.5 个 token（8 帧段只留 4 个 token），这是训练分布外 32 倍的压缩。论文没有报告任何在 k 很小时的行为分析。

论文缺失的两类证据是：其一，把 memory token 随机置换后再做头部截断的对照（若成绩下降不明显，说明位置携带的信息有限，front-loading 被高估）；其二，逐 token 的归因分析，说明第 1–4 个 memory token 究竟覆盖了段内哪些帧。

§ 10 — 最小复现实验 ​

不必复现四阶段训练与 64 卡集群。用公开的 Qwen3-VL-2B 直接测 front-loading 这条假设：

  1. 取 LongVideoBench 验证集若干条，按 8 帧一段构造 Tempo 式输入（系统提示 + 视觉 token + 查询 + 128 个 memory token 位），取最后一层隐状态。
  2. 对每一段，用第 j 个 memory token 的隐状态去回归/检索该段内每一帧的视觉特征，得到一张 128×8 的"token 覆盖哪一帧"热图。
  3. 判据一：若热图呈明显的对角结构（前几个 token 对应前几帧），则位置顺序主要编码时间顺序，头部截断等价于只看段首几帧；若热图弥散且前几个 token 对所有帧都有覆盖，则 front-loading 成立。
  4. 判据二：另做一组端到端对照，在同一预算下比较"头部截断"与"段内均匀间隔取 ki​ 个 token"。后者是一条更强的平凡基线（保留时间覆盖），论文没有测。若两者接近，则消融 C 里头对尾的优势主要来自"尾部截断丢掉了段首"，而不是来自显著性排序。

§ 11 — 最强反例设计 ​

第一重攻击针对消融 D 的归因。 表 tab:ablation_main 的 D 组里，Base Model Prior + 显式路由提示在 LongVideoBench(65.7 对 65.1)、MLVU(76.3 对 75.2)、Video-MME Long(57.3 对 57.0)、LVBench(52.7 对 52.3) 四列上都优于默认配置，唯一劣势是 Video-MME Overall 的 67.6 对 67.7。正文却写"it provides superior comprehensive performance (e.g., 67.7 on Video-MME)"，用唯一赢的那 0.1 点作例证。这是典型的正文与表格错位。反驳实验不需要新数据：把 D 组的五列全部列出并计算平均，若 Base Model Prior 的平均高于默认配置，那么本文关于"Tempo SVLM Prior 更好"的论断就应改写为"两者精度相当，选 SVLM Prior 是因为它省一次前向"。这不否定方法，但会把一条被写成精度优势的结论降级为纯效率论证——而效率论证本身又缺乏支撑（见下一条）。

第二重攻击针对完全缺失的效率测量。 全文反复使用 "O(1)"、"zero computational overhead"、"zero latency"、"single forward pass" 这类措辞，也在消融 C 里以 "O(N2) spatial clustering overhead" 为由否定 Token Merging（而 Token Merging 在 LVBench 上拿到 53.0，高于默认的 52.3）。但论文没有给出任何一张延迟表：没有 wall-clock、没有峰值显存、没有推理侧的硬件型号（训练只写了"64-GPU cluster"，未写 GPU 型号）。反例设计是：在同一硬件上实测 Tempo 与 Token Merging 变体的端到端 TTFT。若两者差距小于 LVBench 上 0.7 点精度所值，那么"O(1) 优于 O(N2)"这条论证就无法支撑放弃 53.0 而选 52.3 的决定。所有效率主张目前都停留在复杂度符号层面。

第三重攻击针对 "less is more"。 4K 与 8K 之间的差距是 0.4（LVBench 52.7 对 52.3）与 0.8（Video-MME Long 57.8 对 57.0）。LVBench 规模下 0.4 点约合个位数题目，论文既没有多次运行也没有置信区间。构造反例只需在 4K 与 8K 下各跑 3 个采样种子，报告均值与标准差。若两档区间重叠，则"更严格的瓶颈起到了去噪作用"这条解释缺乏证据，4K 与 8K 只是打平——而这会同时削弱摘要里"Tempo compresses hour-long videos substantially below theoretical limits"所暗示的那种"越少越好"的叙事。

§ 12 — Follow-up Research Idea ​

驱动它的局限：Tempo 的整条链路是单向且一次性的。压缩器读一遍查询，产出定长 memory，之后无论下游 LLM 在推理中发现了什么，都无法回头要求某一段展开。作者自己在 Discussion 里承认多轮对话下意图变化需要重新抽取整段视频的特征。同时 ATA 的相关性先验是零样本的，从未被下游答案的正确性优化过。

换一个 framing：把压缩从"预处理"改写成"由解码器发起的按需取证"。具体做法是把小 VLM 的输出分成两层：一层是查询无关的、只算一次并可长期缓存的粗粒度全局摘要；另一层是查询相关的高保真锚点，只在全局 LLM 明确请求某个时间窗时才现算。这样上下文里始终只有很少的 token，而"要不要展开"由解码器在推理过程中根据自身的不确定性决定，不再是压缩器的一次性猜测。

可借鉴的相邻领域工具：检索增强生成里的 iterative retrieval-then-read（用生成过程中的不确定性触发下一轮检索），以及推理模型里的 test-time compute 分配（模型自行决定何时停止思考）。两者都提供了"由下游决定上游做多少工"的成熟控制回路。

第一个实验长什么样：先做纯测量，不改架构。在 LVBench 上跑现成的 Tempo(4K)，对每道答错的题记录两件事：ATA 给真值证据所在段落分配了多少 token；以及把该段强制提到 k=128 后是否能答对。这会把失败拆成两类——"分配错了"（提到 128 就对）与"压缩本身丢了信息"（提到 128 仍错）。若前者占多数，说明瓶颈在一次性的分配决策而非压缩容量，按需展开的收益上界很高，此时才值得投入去实现解码器发起的展开机制；若后者占多数，则应优先改压缩器本身而不是控制回路。
