Wan-Streamer v0.2: Higher Resolution, Same Latency ​

项内容
arXiv2607.04443
提交日期2026-07-05
作者Lianghua Huang, Zhi-Fan Wu, Yupeng Shi, Wei Wang, Mengyang Feng, Junjie He, Chen-Wei Xie, Yu Liu, Jingren Zhou, et al.（共 26 位，阿里巴巴 Wan Team；论文封面以团队名义署名，arXiv 元数据列出全部署名人）
分类cs.CV, cs.AI, cs.GR, cs.LG
一句话模型公式一行不改，只把服务拓扑拆成"单卡 thinker + Ulysses 序列并行多卡 performer"，用 K/V 切片作为唯一跨界通信量，把 192p 涨到 640×368 而 200 ms 的模型侧延迟不变。

所属教程：智能体视频生成

§ 1 — 研究问题与重要性 ​

这是一份短技术报告，目标极其收敛：把实时音视频交互模型 Wan-Streamer 的输出分辨率从 192×336 提到 640×368，同时保持 25 FPS 与约 200 ms 的模型侧 signal-to-signal 延迟不变。

为什么分辨率是个真问题。v0.1 的 192p 输出只够支撑近景视频通话式构图 —— 脸部反应和说话行为保得住，但一旦拉宽景别，身体姿态、手部、附近物体与场景布局就被压缩到不可读。而"看得懂周围环境"恰恰是把一个对话头像升级成 scene-grounded agent 的前提：agent 的注视方向指向什么、手在操作什么、它与场景里的物体是什么空间关系，这些都需要中景构图才成立。

为什么延迟不能让步。论文把约束点说得很清楚：这是被流式因果性而非离线渲染质量约束的问题。每个 160 ms 的单元里必须完成一整套动作 —— 处理当前用户观测、更新共享交互状态、生成同步的语音与视频 latent、解码上一个单元、发出响应 —— 而且不能拉长交互节奏。加上 350 ms 的双向网络预算，端到端远程交互延迟约 550 ms。分辨率提升带来的计算量增长如果落在这条路径上，交互就崩了。

§ 2 — 前人工作与不足 ​

论文把自己放在四条线的交叉处。全双工语音对话（Moshi 及相关综述）已经证明自然对话不该被简化为 ASR–LLM–TTS 的轮流制。Omni-modal 模型（Qwen3-Omni、MiniCPM-o 4.5）把感知扩展到图像、视频、音频输入。视频生成与因果 rollout 方法（Wan、Diffusion Forcing、Self-Forcing）提供了流式视觉合成的基础。实时数字人一侧（VASA、StreamAvatar、MAVID、Body of Her）推进了音频驱动人脸、流式视觉 agent 与端到端具身交互。

v0.1 的贡献是把这些拼在一起的方式换掉了：用户与 agent 的文本、音频、视频被表示在同一条因果时间线上，由单个 Transformer 建模，而不是像级联式视觉 agent 系统那样把感知、响应时机、语音、可见的倾听行为、同步视频响应分散在多个模块里。这样做的好处是这些量共享同一个因果交互状态。

而 v0.1 留下的缺口就是本文要补的：192p 限制了视觉范围。这是一个纯粹的工程性缺口 —— 不是建模能力不足，而是同样的建模在更高分辨率下装不进延迟预算。

§ 3 — 重建作者的思考路径 ​

要在不动模型公式的前提下吃下更高分辨率，只能从服务拓扑下手。第一个判断是：成本增长不是均匀的。分辨率翻几倍，涨的几乎全在视觉 latent 的去噪路径上；感知编码、语言/状态更新、解码这些环节的开销基本不随视觉分辨率线性膨胀。既然增量是局部的，就应该把额外硬件精准地投给那一块，而不是整体加卡。

第二个判断关乎并行方式的选择。视觉 latent 序列在高分辨率下变得很长，长序列正是 sequence parallelism 的适用场景 —— DeepSpeed-Ulysses 这类方法把序列切到多卡上，在 attention 前后用 all-to-all 在"按序列切"与"按 head 切"两种布局之间转换（文献已有结论）。音频 latent 的 token 数则少得多，切它只会让通信开销盖过并行收益，所以不切。

第三个判断是拆分界面该放在哪。如果 thinker 与 performer 之间要传语言序列本身，那 performer 组内部还得再维护一份语言序列的并行方案，边界就不干净了。但注意到一个事实：thinker 的语言/状态计算最终只以 K/V cache 的形式参与生成。那就只传 K/V 切片，语言序列根本不进 performer 组。边界因此保持紧凑，增量成本被完全隔离在 performer 里。

§ 4 — 核心 Intuition ​

延迟和吞吐是两件事。响应延迟是编码→状态更新→latent 生成→解码这条 signal-to-signal 路径的长度，吞吐要求的是"performer 组耗时 + thinker–performer 传输 + 组内 Ulysses 通信"要塞进一个 160 ms 单元。分辨率提升只加重了后者中的一项，于是把这一项搬进一个序列并行的 performer 组，用更多卡把它的墙钟时间压回单元预算内，而延迟关键路径上的 thinker 保持单卡不动。因为语言/状态的贡献早已被折叠进 K/V，跨界只需要传 K/V 切片和 latent。

§ 5 — 具体方法与完整 Pipeline ​

模型侧完全继承 v0.1 的 native-streaming 公式：用户文本、音频、视频观测更新同一份历史，这份历史条件化 agent 的文本、语音、视频响应；生成的音视频 latent 在每个单元后被写回历史，所以下一次响应既依赖用户的近期行为，也依赖 agent 自己上一步的表达。v0.2 只在这个公式外围做了两件事：视觉目标从 192p 换到 640×368，训练数据的重心从以近景通话构图为主移向更宽的、有场景依托的对话设定。

部署拆成两个角色，以流式单元 k 为例：

  • Thinker（单卡）。承载因果音视频编码器、负责语言与状态更新的 token-causal Transformer 路径、KV-cache 构建，以及把返回的 latent 转成输出音视频的因果解码器。在单元 k 上，它消费当前用户观测，产出一份新的、performer 可直接使用的 K/V 切片；大约在同一个边界上，它接收上一个单元生成好的 latent，解码并发出响应。
  • Performer（Ulysses 式上下文并行组）。承载昂贵的 flow-matching latent 生成路径。每个 rank 持有预分片的 K/V cache，收到当前 K/V 切片后更新自己那一片全历史 cache，然后对下一个单元跑上下文并行的去噪。高分辨率视频 latent 是主要的序列并行路径，切分到各 rank 上，attention 前后用 all-to-all/gather 通信，且这些通信全部留在 performer 组内部。音频 latent 因为短得多，不做序列切分。

这个调度的要点在于把 thinker 与 performer 的工作错开在相邻单元上（thinker 在解码上一单元的同时为下一单元准备条件），并且使跨界通信只包含两类内容：thinker 广播的 K/V 切片，以及回传的 latent。语言/状态计算已经被折叠进 K/V，不需要在 performer 组里单独存在一条语言序列。

§ 7 — 实验设计与结论 ​

必须先说清楚这份报告的实验体量：它只有延迟测量与定性视觉观察两部分，没有 benchmark、没有 baseline 对比、没有 ablation、没有任何视觉质量的定量指标。

延迟怎么定义的？ 沿用 v0.1 的响应边界：模型侧 signal-to-signal 延迟从"一个 160 ms 的用户流式单元对 thinker 可用"开始计时，到"对应的音视频响应单元已被解码待发出"结束。在第 3 节的服务路径下，v0.2 在产出 640×368 / 25 FPS 视频的同时保持约 200 ms 模型侧延迟；沿用 v0.1 相同的 350 ms 双向网络预算，远程交互总延迟仍约 550 ms。作者明确把网络项当作外部部署假设保留，以便对比只隔离模型侧与服务侧的变化，并声明带宽受限的传输效应不在此处的测量范围内。

为什么不和别人比？ 论文给了一个诚实的理由：公开的实时系统各报各的端点 —— 有的报首包语音延迟，有的报首帧延迟，有的报 FPS，有的报音画延迟，有的报产品级响应时间。因此作者选择保持 v0.1 的测量约定，在同一个响应边界上报告 v0.2 的运行时。这个选择让版本间对比是干净的，但也意味着与外部系统的横向比较无从建立。

视觉侧的结论是什么？ 用生成的 640×368 对话作为升级后输出格式的定性观察，检查重点是倾听与说话两个区间内的视觉稳定性与可读性，包括面部细节、注视、口部运动、手部、姿态、附近物体与局部场景布局。结论表述得也很克制：v0.2 的输出格式是"更清晰的近景通话 + 有场景依托的中景 agent"。

§ 8 — Take-aways ​

5 句话版：实时音视频交互模型提分辨率的难点不在建模而在延迟预算。Wan-Streamer v0.2 一行模型公式没改，只重划服务拓扑：延迟关键路径（感知、语言/状态更新、K/V 构建、解码）留在单卡 thinker，昂贵的高分辨率 latent 去噪搬进 Ulysses 式序列并行的多卡 performer。关键设计是跨界只传 K/V 切片 —— 因为语言/状态的作用早已折叠进 K/V，performer 组内不需要存在语言序列。音频 latent 太短不切分，避免通信开销盖过并行收益。结果是分辨率从 192×336 到 640×368，200 ms 模型侧延迟与 550 ms 端到端延迟均不变，代价是 GPU 数量增加。

3 句话版：把增量计算精准隔离到非延迟关键的并行组里。K/V 作为唯一的跨界接口，让边界保持紧凑。分辨率涨了三倍多，延迟一分没涨，卡数变多了。

1 句话版：延迟不变的分辨率升级，靠的是服务拓扑而不是模型。

§ 9 — 最脆弱的假设 ​

最脆弱的一条是：160 ms 的单元预算能稳定容纳"performer 组耗时 + 跨界传输 + 组内 Ulysses 通信"这个和。论文自己把这个约束写成了实时吞吐的充要条件，但报告的所有延迟数字都是单点值（"约 200 ms""约 550 ms"），没有分布、没有尾部延迟、没有在多少并发会话下测得。

这个假设为什么容易失效：Ulysses 式并行的 all-to-all 是集合通信，其耗时由组内最慢的 rank 决定，对网络抖动与 GPU 间带宽争用高度敏感。单会话独占一组 GPU 时它很稳，多会话共享集群时尾部延迟会显著恶化。而交互体验是被尾部而非均值决定的 —— 每二十个单元里有一个超出 160 ms，用户感知到的就是卡顿而非"平均很快"。

论文提供的证据只有沿用 v0.1 约定的单点运行时测量，缺的关键证据是：P95/P99 单元耗时、并发规模下的延迟曲线、以及 performer 组规模从若干卡变化时通信开销与计算收益的交叉点。最后这一项尤其重要 —— 序列并行的加速比随 rank 数增长会因通信占比上升而饱和甚至反转，而论文从头到尾没有给出 performer 组的实际卡数，也没有给出任何 scaling 曲线。因此"更高分辨率、同样延迟"这个标题成立的硬件代价是未知量。

§ 10 — 最小复现实验 ​

不复现模型，只检验拓扑设计的核心命题："把长视觉序列的去噪切到多卡上，能在 160 ms 内完成，且通信不吃掉收益"。

用任一开源的 DiT 视频扩散骨干（Wan 系即可），构造两组 latent 序列长度，分别对应 192×336 与 640×368 在相同时间窗下的 token 数。实现一个最小的 Ulysses 式序列并行 attention（切序列 → all-to-all → 按 head 算 attention → all-to-all 切回），在 1/2/4/8 卡上分别测单步去噪的墙钟时间，并把计算时间与通信时间分开计时。同时测一次"K/V 切片广播 + latent 回传"的跨界传输耗时。

支持论文的结果是：在高分辨率序列长度上，某个卡数下（计算 + 通信）明显低于 160 ms，且通信占比仍在可接受范围。反驳的结果是：通信时间随卡数增长很快，使总时间在任何卡数下都压不进预算，或者压进去所需的卡数高得离谱 —— 那说明这个拓扑的可行性严重依赖论文未披露的互联条件（例如 NVLink 全互联），换到普通 PCIe 机器上不成立。补充测一组：把音频 latent 也做序列切分，验证论文"切了反而更慢"的判断是否在你的序列长度下同样成立。

§ 11 — 最强反例设计 ​

替代解释攻击："same latency" 的成立可能部分来自测量边界的选择，而非拓扑的功劳。论文定义的模型侧延迟起点是"用户单元对 thinker 可用"，终点是"响应单元已被解码待发出"。这条边界把两件事排除在外：一是跨界传输与 performer 计算的相当一部分被流水线错位吸收了（thinker 在解码上一单元时 performer 在算下一单元），二是网络传输被显式声明为外部假设。

于是可以设计这样一个攻击：测量端到端的用户感知延迟 —— 从用户实际发声的物理时刻，到对应的 agent 视频帧出现在用户屏幕上的物理时刻，中间包含采集、编码、上行、排队、模型、下行、解码、显示的全部环节。如果这个数字在 v0.1 与 v0.2 之间有可观差异，而模型侧指标显示"不变"，那就说明该指标虽然对模型迭代是个有用的内部量，却不能支撑"用户体验不变"这个更强的读法。论文对此其实有部分自觉（它说带宽受限的传输效应不在测量范围内），但这个免责声明反过来削弱了标题所暗示的结论强度。

第二类可预测失败：流水线错位使 agent 的反应窗口变长。thinker 在单元 k 上接收观测并产出 K/V，performer 用它去算单元 k+1，而 thinker 在同一边界上解码的是单元 k−1 的产物。这意味着从"用户做了某个动作"到"agent 的视频响应体现出这个动作"之间隔了不止一个单元。近景通话里这个滞后不易察觉，但在中景、场景依托的交互里 —— 恰恰是 v0.2 主打的场景 —— 用户举起一个物体、agent 的注视要跟过去，这类视觉互动的时间对齐会把滞后暴露出来。论文只报告了定性观察且检查项集中在"稳定性与可读性"，没有任何针对响应时间对齐的评估。

第三点是版本对比的公平性：v0.2 同时改了三样东西 —— 分辨率、服务拓扑、训练数据重心（从近景通话转向更宽的场景依托设定）。定性观察里"中景 agent 更可读"这个结论无法区分是分辨率的功劳还是数据重心转移的功劳。

§ 12 — Follow-up Research Idea ​

驱动局限：分辨率是全局且固定的。整帧以同一规格生成，而交互场景的信息密度分布极不均匀 —— 说话时嘴部区域每帧都在变且承载全部音画同步信息，背景墙面可以几秒不更新，手部只在有操作时才重要。用统一分辨率覆盖最坏情况，等于为最挑剔的区域给整帧买单，而这正是为什么"提分辨率"会变成一个需要动服务拓扑才能解决的难题。

新 framing：把 latent 的计算预算从"每单元固定"改成"按感知重要性动态分配"，即在流式生成里引入空间与时间上的自适应 token 预算。同一个 160 ms 单元内，嘴部与手部区域分配更多 token 与更多去噪步，静态背景区域复用上一单元的 latent 并只做极少量更新。这把"提分辨率"从一个纯粹的算力问题，转成一个预算分配问题 —— 而后者可以在不加卡的前提下继续提升有效清晰度。

可借鉴的相邻领域工具：一是视频编解码里的率失真优化与运动补偿 —— 编解码器几十年来就在做"按块分配码率、静态区域直接跳过"这件事，其宏块级的失真—码率权衡框架可以直接类比到 latent token 的预算—质量权衡。二是注意力稀疏化与 token 剪枝在长序列推理中的成熟做法，它们提供了在 attention 层面按重要性丢弃或合并 token 的现成算子，而这恰好也能缓解 Ulysses 并行下通信量随序列长度线性增长的压力（序列变短，all-to-all 的负担同步下降）。

第一个实验：先做一个纯离线的可行性测量，不碰实时系统。取一批真实的对话视频，在 latent 空间统计每个时空区块在相邻单元间的变化幅度，画出"变化能量的空间分布"。若结果显示能量高度集中在很小的比例区域上（推测嘴部加手部会占据绝大部分变化能量，但这需要实测确认），说明固定预算存在巨大浪费，自适应分配的上限值得追求；随后离线验证第二步 —— 在低变化区域强制复用上一单元 latent，测量重建质量下降与节省的 token 数之间的曲线。若曲线在很宽的区间内平坦，就能给出一个可直接接进流式管线的预算策略；若质量迅速劣化，说明 latent 的时间冗余没有想象中那么大，这条路应及早放弃，转而在服务拓扑上继续深挖。
