Adapting VACE for Real-Time Autoregressive Video Diffusion ​

项内容
arXiv2602.14381
提交日期2026-02-16
作者Ryan Fosdick
分类cs.CV, cs.AI
一句话把 VACE 的参考图从扩散 latent 序列里拿出来、改走一条并行的 Context Block 条件通路，从而在不重训、不改预训练权重的前提下让固定 chunk 大小与 KV cache 得以保留，把结构控制、inpainting、时序延展搬进实时自回归流式管线。

所属教程：自回归视频生成

说明

本文是单作者技术报告（Ryan Fosdick，Daydream），10 页 4 图 7 表，参考实现在 github.com/daydreamlive/scope。全文没有与 batch VACE 的画质对比、没有 baseline 对照的控制精度评测、没有消融，作者在 §9 显式说明了原因。本站论文索引里该条目名为 "AR"、别名"适配 VACE 实时 AR"，是描述性名称而非编号错误。Table 5/6/7 的表头在 HTML 中未渲染，列义按正文说明确定为「每 chunk 延迟 / 两列 FPS / 峰值显存」。

§ 1 — 研究问题与重要性 ​

实时视频生成模型（LongLive、Krea Realtime Video、StreamDiffusion V2）用因果注意力逐 chunk 生成，每个 chunk 只看自己和过去，因此可以做 KV cache、显存有界。代价是它们几乎没有 batch 模型那套控制能力：参考图引导、结构条件（深度/姿态/光流/线稿/布局）、局部编辑。而这些能力恰恰是把"能生成视频"变成"能用视频做事"的关键——直播换装、实时抠像重绘、按草图驱动画面，都要求控制信号能逐帧进入。

从头训一套流式可控模型代价极高。VACE 已经把这一整套控制统一在一个框架里，而且训练方式是 Context Adapter Tuning：base DiT 冻结，只训一组并行的 Context Block，产生 hint 通过零初始化线性投影加回主干。问题在于 VACE 假设双向注意力、一次处理整段序列，与流式管线互斥。本文要回答的是一个非常具体的工程问题：这套已经训好的权重，能不能一行不重训地搬进因果 chunk 管线。

§ 2 — 前人工作与不足 ​

流式自回归侧。LongLive、MemFlow、Krea Realtime Video、Reward Forcing 都是 Wan2.1 系的因果 chunk 管线，共同约束是固定 chunk 大小与持久 KV cache。它们能做的控制基本只有文本 prompt 和首帧。

控制侧。VACE 支持 reference-to-video、video-to-video 结构控制、掩码编辑（inpaint/outpaint）、时序延展及任意组合，输入是 src_video / src_mask / src_ref_images 三件套。它的不足不是能力问题而是架构问题，论文点得很具体：VACE 把参考帧直接拼进扩散 latent 序列，用双向注意力处理，去噪后再把参考帧从输出里剥掉。这在流式里有三处不兼容——(1) 不同任务参考帧数量不同，序列长度可变，破坏固定 chunk；(2) KV cache 污染：拼进去的参考帧会被当成"已生成的历史"缓存并被后续 chunk 注意到，语义上就是错的，而且 RoPE 位置编码已经烘进缓存的 K/V 里，事后想摘掉参考帧就得重算整个 cache；(3) 每步去噪后都要识别并移除参考帧，额外开销。

实时可控生成的直接对手是 MotionStream，它靠从双向 teacher 做全模型蒸馏，在轨迹控制这一种模态上质量更高。本文的定位是另一端：不训练、复用现成权重、支持多种控制类型及任意组合，代价是单任务质量不如专门蒸馏的模型。作者自己把这个取舍写清楚了。

§ 3 — 重建作者的思考路径 ​

起点是一个工程观察：VACE 的三类输入里，src_video 和 src_mask 天然是逐帧对齐的，它们本来就可以按 chunk 切开、逐 chunk 处理；只有 src_ref_images 是"整段共享的一组图"，而 VACE 偏偏把它塞进了 latent 序列。也就是说，不兼容并非来自 VACE 的控制机制本身，而是来自参考帧的入口位置。

第二步是问：参考帧为什么非得进 latent 序列？因为 VACE 依赖双向注意力让 video latent 去"看"参考帧。但 VACE 的架构里本来就有一条并行通路——Context Block 产生 hint、经零初始化投影加进 DiT。如果参考帧改走这条通路，video latent 序列就永远只含视频，chunk 大小固定，KV cache 干净。

第三步是判断权重能不能直接复用。Context Adapter Tuning 的结构决定了：Context Block 的职责是"把条件编码成 hint"，注入方式是残差加法配零初始化投影。改动只发生在参考帧从哪里进入、hint 往哪里注入，Context Block 内部的权重与投影结构都没变。因此可以推断权重在新架构下仍然有效——这个推断需要实验验证，而验证结果是分裂的：结构控制与掩码这类 hint 在空间上局部的任务迁移良好，而 reference-to-video 严重退化，因为原来的 Context Block 依赖参考图与 video latent 之间的 cross-attention，而这正是被砍掉的那部分。

第四步是缓存工程：VACE 用 inactive/reactive 双流编码，流式下 3D VAE 内部有跨 chunk 状态，两条流必须分开缓存以免时序统计互相污染；inpaint/outpaint 还要跳过 reactive 流的缓存，否则每 chunk 新生成的内容被时序混合会产生 ghosting。

§ 4 — 核心 Intuition ​

VACE 与流式生成的冲突不在控制机制，而在参考帧的入口：把它拼进扩散 latent 会同时破坏固定 chunk、污染 KV cache、把 RoPE 焊死在缓存里。VACE 自己已经有一条并行的 hint 通路，把参考帧改从那里进入，视频序列就只剩视频，chunk 大小和缓存都保住了；由于 hint 的注入方式是残差加法配零初始化投影，Context Block 的权重在新入口下依然成立，不用重训。

§ 5 — 具体方法与完整 Pipeline ​

以 LongLive 1.3B 做"深度图驱动的实时 V2V"为例，368×640、每 chunk 12 帧、4 步去噪：

  • 一次性：参考图（若有）经 VAE 编码后送入 Context Block，算出 hint，之后每个 chunk 复用（延展模式下尤其如此）。
  • 每 chunk：输入帧提取深度图作为 src_video，与 src_mask 一起按 inactive/reactive 双流分别经 TAE 编码（两条流各有独立的编码器 cache），channel 维拼接后进 Context Block 得到该 chunk 的 hint。
  • 注入：video latent 单独去噪，第 i 个 DiT block 通过残差加法接收对应 Context Block 的 hint，缩放系数为用户可控的 context scale α（本文全程用默认 α=1.0，未调）。
  • 缓存策略：条件类模式（深度、姿态等）两条流都缓存；inpaint/outpaint 与 I2V 延展跳过 reactive 流缓存。KV cache 跨 chunk 持久保留。
  • 输出：解码出该 chunk 的帧，17.2 FPS。模式由提供了哪些输入隐式推断，没有显式 mode 参数；掩码可由 YOLO 这类实时检测器动态驱动，inpaint 可与 LoRA 组合做局部风格迁移。
  • 验证范围：五条 Wan2.1 系管线（LongLive、StreamDiffusion V2、MemFlow、Krea Realtime Video、Reward Forcing），1.3B 与 14B 两个规模共用同一份适配代码。

§ 6 — 核心数学推导 ​

本文的形式化只有一个式子，但它恰好是"为什么不用重训"的全部依据。第 i 个带对应 Context Block 的 DiT block 通过残差加法接收 hint：

xi​=DiTBlocki​(xi−1​)+α⋅Wproj(i)​hi​

其中 hi​ 是第 i 个 Context Block 输出的 hint，Wproj(i)​ 是零初始化的线性投影，α 是 context scale。

理解这个式子要抓两点。第一，Wproj​ 初始化为零意味着训练开始时 hint 完全不起作用，主干输出与冻结的原模型逐位相同——这是 ControlNet 一脉相承的设计，保证微调过程从"不破坏预训练模型"出发。第二，也是本文论证的核心：这个式子里没有任何一项引用参考帧在序列中的位置。hi​ 怎么算出来的、xi−1​ 里有没有参考帧的 token，对这条残差路径的形式没有影响。因此把参考帧从 x 里挪到 h 的计算路径上，Wproj(i)​ 学到的权重仍然作用在同一个残差位置上、仍然作用在同样维度的特征上。

但这个论证只覆盖了注入侧，没有覆盖产生侧。原 VACE 的 Context Block 在完整序列（参考帧 + 视频）上运行，其内部注意力可以让参考帧与 video latent 互看；适配后 Context Block 只吃参考帧（见 Table 1 的对照）。式 (1) 的不变性保证了 hint 加得进去，保证不了 hint 的内容仍然合适。论文的实验结果与这个分析一致：结构控制与掩码（hint 空间上局部、与 video latent 的交互本来就弱）迁移成功，reference-to-video（依赖 cross-attention）严重退化。

§ 7 — 实验设计与结论 ​

全部是 inference-only 的性能测量，每个配置跑 15 个 chunk（前 3 个 warmup），bfloat16 + TAE decoder。作者明确说明未测端到端流式吞吐。

问题一：适配后开销多大？ LongLive 1.3B（RTX 5090 32GB，SageAttention，368×640，12 帧/chunk，4 步）：baseline 539 ms / 22.3 FPS / 13.2 GB；加深度控制 698 ms / 17.2 FPS / 14.6 GB；加 inpainting 698 ms / 17.2 FPS / 14.6 GB；加 I2V 延展 534 ms / 22.5 FPS / 14.6 GB。显存开销约 +1.4 GB（就是 Context Block 权重）。Krea Realtime Video 14B（H100 80GB，FlashAttention 2，320×576）：baseline 741 ms / 16.2 FPS / 45.2 GB；深度 887 ms / 13.5 FPS；inpainting 958 ms / 12.5 FPS；延展 965 ms / 12.4 FPS，显存几乎不变（45.1 GB）。结论是 20–30% 的延迟开销、可忽略的显存代价，1.3B 上仍在 17 FPS 以上。

这里有一处需要如实指出的不一致：论文称延展模式因为参考 hint 只算一次而开销可忽略（约 1%），"这个好处在 14B 上不明显，因为 base model 主导延迟"。但 14B 上延展模式是三种模式里最慢的（965 ms，+30.2%），而 base model 主导延迟本该让相对开销变小。1.3B 上延展确实比 baseline 还快 5 ms（534 vs 539），但这个差值在测量噪声量级内。给出的解释与数字方向相反。

问题二：控制真的起作用吗？ Table 7 只报两个能客观测量的模式（LongLive 1.3B，5 个 chunk）：深度 RMSE 0.157（用 Video Depth Anything 从输出里反提深度，与输入深度图比），掩码保留 SSIM 0.983（未掩码区域输入输出的 SSIM）。作者明确声明"这些指标确认控制在流式模式下工作，绝对值不能与 ControlNet++ 这类 batch 基准直接比较"。这张表没有任何 baseline 或对照——没有 batch VACE 的同指标、没有关掉控制的对照、没有 context scale 的扫描。§4 里"control adherence is preserved（Table 7）"的措辞比这张表能支撑的强：表只能说明控制生效，说明不了相对 batch 模式"保持"了多少。

问题三：哪些能力没迁移成功？ §9 的 limitations 相当坦率：reference-to-video 的细节保持与参考保真度相比 batch VACE 严重退化，需要进一步的架构工作；first+last frame 延展因为流式 chunk 太小而用处有限；100 帧以上不重新锚定会时序退化；部分控制信号（深度、线稿、布局）可靠，其余需要更多调参。最关键的一条是作者自己写的：全文没有提供与 batch VACE 的感知质量对比，理由是自回归 base model（如 LongLive）与 Wan2.1 在注意力模式、步数、训练数据上都不同，直接比会把 base model 的差异与本文的架构改动混在一起，无法归因。

§ 8 — Take-aways ​

5 句话版：VACE 与流式自回归的不兼容不在控制机制，而在参考帧被拼进了扩散 latent 序列，这会同时破坏固定 chunk、污染 KV cache、把 RoPE 焊进缓存。把参考帧挪到并行的 Context Block 通路后，视频序列只剩视频，固定 chunk 与 KV cache 都保住了。由于 hint 的注入形式是零初始化投影 + 残差加法，与参考帧在序列中的位置无关，预训练的 Context Block 权重可以直接复用，一步都不用重训。代价是 20–30% 的每 chunk 延迟与约 1.4 GB 显存（1.3B），1.3B 上仍能跑 17 FPS。真正的分界线是 hint 的空间局部性：结构控制与 inpainting 迁移成功，reference-to-video 因为原本依赖参考图与 video latent 的 cross-attention 而严重退化。

3 句话版：条件注入的接口设计（零初始化残差）比条件的具体内容更能决定权重能否跨架构迁移。把参考帧从 latent 序列移到并行通路，就把 VACE 的大部分能力零成本搬进了实时管线。搬不动的那部分，恰好是本来就依赖双向注意力的那部分。

1 句话版：改参考帧的入口，不改 VACE 的权重。

§ 9 — 最脆弱的假设 ​

最脆弱的是"结构控制与掩码的控制精度在流式适配后被保持"这一判断，方法的实用价值几乎全押在它上面——因为 reference-to-video 已经被作者自己判定失败，剩下能卖的就是 V2V 与 MV2V。

支撑它的全部证据是 Table 7 的两个孤立数字：深度 RMSE 0.157、掩码 SSIM 0.983。这两个数没有任何参照系。作者自己也承认它们与 batch 基准不可比，并在 §9 里说明为什么不做 batch VACE 对比（base model 混淆）。但这个理由只排除了"与 batch Wan2.1+VACE 直接比"，并没有排除同一个流式 base model 内部的对照：关掉 VACE 让模型自由生成，再对输出提深度、与同一份输入深度图算 RMSE，得到的就是"完全不控制"的下界；把 context scale α 从 0 扫到 1，就能画出控制强度-精度曲线。这些对照与 base model 无关，本可以做而没做。

如果这条假设不成立——比如 0.157 的 RMSE 实际上离"不加控制"的基线没多远——那么本文的贡献就退化为"能跑通、不崩"的工程记录，而不是"控制能力被保留"的结论。α=1.0 全程未调这一点让担心更具体：一个从未被扫描过的超参，说明控制强度这条轴根本没被检验。

§ 10 — 最小复现实验 ​

一周内可做，代码已开源（daydreamlive/scope），不需要训练：

  1. 装好 LongLive 1.3B + 本文适配，跑通深度控制模式，复现 539/698 ms 的延迟数字确认环境正确。
  2. 造一个 20 段视频的小测试集，用 Video Depth Anything 提取输入深度图作为控制信号。
  3. 补上论文缺的对照：同一批 prompt 与输入，跑四组——(a) 不加 VACE 的纯文本生成；(b) α=0；(c) α=0.5；(d) α=1.0。每组都从输出反提深度，与输入深度图算 RMSE。
  4. 判据：若 (a)/(b) 的 RMSE 与 (d) 的 0.157 接近（比如都在 0.15–0.20），说明这个指标对控制强度不敏感，Table 7 不构成"控制被保持"的证据；若 (a)/(b) 显著更差（比如 0.4 以上）且随 α 单调下降，则论文的判断成立，并且顺带给出了本该有的控制强度曲线。
  5. 附加一组零成本验证："KV cache 污染"这条动机是否真的重要：故意把参考帧拼回 latent 序列（模拟原 VACE 做法）跑几个 chunk，看输出是否出现作者预期的退化。这能直接检验 §3.1 三条不兼容里最关键的那条是不是真问题，还是只是理论隐患。

§ 11 — 最强反例设计 ​

最有力的攻击是给"权重可直接迁移"提供一个替代解释：hint 之所以在新架构下还能用，可能不是因为 Context Block 学到的表示与位置无关，而是因为 α=1.0 下 hint 的实际影响本来就很弱，弱到迁移与否看不出差别。

设计实验分辨：在同一批输入上，同时记录 (i) 加 hint 与不加 hint 时主干中间激活 xi​ 的相对变化幅度 ∥αWproj​hi​∥/∥DiTBlocki​(xi−1​)∥ 逐层的分布，(ii) 同样的量在原 batch VACE 上的分布。如果适配后这个比值比 batch 模式下小一个数量级，那么"迁移成功"的真正含义是"hint 影响被稀释了"，控制看起来还在只是因为结构信号本来就通过 src_video 逐帧对齐地进来、空间对应关系强到即使弱注入也能生效。这个解释与论文自己的发现是自洽的：reference-to-video 没有逐帧空间对应，一旦注入变弱就立刻崩——论文把这归因于 cross-attention 缺失，但"注入被稀释"是同样能解释数据的替代假说，而且更简单。

第二条攻击线针对 14B 的延展模式：965 ms、+30.2%，是全表最慢，与论文"参考 hint 缓存后开销可忽略"的机制解释方向相反。如果这个数字是真的，说明适配在大模型上的开销来源并未被理解清楚，作者给出的 profiling 粒度（只有每 chunk 总延迟）不足以支撑任何机制性结论。补一次逐模块的 profiling 就能判定：如果 14B 延展的额外时间不在 Context Block 而在 TAE 缓存管理或掩码编码上，那么"参考 hint 只算一次"这个优化在实践中根本不是瓶颈所在。

§ 12 — Follow-up Research Idea ​

驱动局限：本文最有价值的负结果是 reference-to-video 的失败，而失败原因被诊断为"Context Block 原本依赖参考图与 video latent 的 cross-attention，因果流式砍掉了这条路"。目前的处理是承认失败、留待未来的架构工作。但这个诊断本身指向一个更一般的问题：身份/风格这类全局条件，与深度/掩码这类逐帧对齐条件，在流式生成里需要根本不同的注入机制，而现有框架用同一套 Context Block 处理两者。

新 framing：不要把参考图当成"另一种条件输入"，而是把它当成流式生成的持久状态的一部分——与 KV cache 同级的、可读可写的记忆，而不是每 chunk 重新注入的外部信号。可借鉴的相邻领域工具是检索增强生成里的 memory 读写机制，以及 LLM 里的 prefix/prompt tuning：给自回归视频模型开一段专用的、位置编码与视频时间轴解耦的"参考前缀"，它进入注意力但不进入时间序列、不参与 RoPE 的时间外推、也不会被后续 chunk 当作历史帧。这样参考图既能被 video latent 通过注意力直接读取（补回被砍掉的 cross-attention），又不破坏固定 chunk 与因果性。

第一个实验：在 LongLive 1.3B 上实现"解耦位置编码的参考前缀"，把 VACE 的参考图 token 挂在这个前缀上而非 Context Block 上，仍然冻结所有权重（前缀只需要一个位置编码偏移，无新参数）。用同一组人像/物体参考图，与本文的 Context Block 方案对比身份保持度（比如输出帧与参考图的 DINO/CLIP 特征相似度），同时测延迟与显存。如果零训练的前缀方案就能把 R2V 从"严重退化"拉回可用，说明这个失败是位置编码与缓存语义的问题而非表示能力的问题，那么整个"如何把 batch 控制搬进流式"的问题应该围绕条件的时间语义重新组织，而不是围绕条件的模态。
